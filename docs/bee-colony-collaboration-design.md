# newbee 协作系统设计 v2：围绕工作完成的蜂群

> 状态：v2 产品与实现约定。核心工作流已在独立工作树落地；具体实现、实测结果和未覆盖范围以实现记录为准。
> 范围：组织关系、工作流程、信息传递、界面交互、执行控制、跨主机与验证。
> 实现与验证记录见 [colony-implementation.md](colony-implementation.md)。本设计中的目标不等同于已验证能力，旧 HTML 原型仅供样式参考。

## 1. 目标与取舍

让用户用自然交流提出研发目标，由系统持续推进，交付可检查、可验证、可接续的成果。用户把精力花在目标、重要取舍和验收上。

成功标准：在交付质量不下降的前提下，降低用户投入时间、重复解释、无效等待和返工；模型成本应与实际收益相称。增加 AI 数量、群聊消息数或工具调用数不是成功标准。

默认决策：

- 一个工作项有一个负责人；小任务由一个 AI 完成，必要时引入协作者。
- 群聊是共同沟通入口，成员对话复用原有 newbee 开发界面。
- 用户无需填写任务表；系统内部必须保存明确的工作记录。
- 工作目标、约束、证据与成果跨会话保存，不能依靠聊天记忆维持。
- 多 AI 提案、讨论、拆分、独立验证按任务价值和风险启用，不作为固定开工仪式。
- 常用控制有可见按钮，自然语言提供同等入口，不要求记命令。
- 运行环境自动选择；权限、远端连接及不可逆操作仍需真实授权。

### 1.1 需要解决的现有问题

前期调研发现 Coordinator/Hive 与 CrossHost 的组织、成员和生命周期语义交叠；之后 Colony 设计又累积了信号、刺激强度、讨论、孵化及多种入口。

| 问题 | v2 的决定 |
|---|---|
| 会话、组、主机之间的关系难理解 | 组织、工作、会话、运行环境分别建模，日常界面只突出群、成员、工作、成果 |
| 群聊与工作轨迹都能下指令 | 指令从聊天或明确按钮进入；轨迹只用于查看和核查 |
| 不知道谁在干什么 | 成员行默认显示真实活动和更新时间 |
| 每件事都讨论、批准、再开工 | 明确且已授权的请求直接执行；关键歧义和重大取舍再询问 |
| 全员广播导致重复劳动 | 通知范围与执行责任分开，一个工作项只有一个当前负责人 |
| AI 自称完成就被当成交付 | 完成必须带成果、验证证据及已知限制 |
| 跨主机配置影响日常使用 | 连接发现与环境匹配自动化，认证与项目授权有明确边界 |

### 1.2 蜂群类比的边界

借鉴真实蜂群的局部信息、灵活分工、共享环境信号和个体失效后的接续能力。蜂王主要承担繁殖职能，不是任务总指挥；蜂群行为也不能直接证明多 AI 研发更有效。

软件研发额外需要明确责任、版本一致性、访问控制和可验证交付。因此不引入强制 Queen 角色，不靠投票决定技术正确性，不靠自发竞争领取代替责任管理。成员在组织上平级，工作内可以临时协调；管理员是权限角色。

## 2. 核心模型

| 对象 | 定义与关系 | 用户通常在哪里看到 |
|---|---|---|
| Colony 蜂群 | 围绕项目或共同目标的协作空间；有成员、工作、群聊和共享成果 | 左侧群列表与群聊 |
| Bee 成员 | 稳定的人或 AI 身份；可加入多个群；AI 身份不等于某一段会话 | 成员列表、头像、对话 |
| Work 工作项 | 目标、范围、负责人、约束、状态和验收条件的持久记录；归属一个群 | 群内工作卡与详情 |
| Honey 成果 | 面向交付的代码变更、文档或结论，关联工作版本和验证证据 | 成果卡与工作详情 |
| Session 会话 | 一段沟通或执行上下文；成员可拥有多段会话，工作可跨会话接续 | 点成员后的会话列表 |
| Garden 环境 | 绑定主机的执行与资源边界；不同主机属于不同 Garden | 自动匹配，必要时在详情显示 |
| Tools 工具 | 在环境与权限范围内可用的能力 | 保持现有工具输出与权限交互 |
| Event 事件 | 消息、状态变化、工具活动和执行回执的记录 | 群内摘要及只读详情 |

关系约束：

- 一个群可使用多个 Garden，一个 Garden 可在授权范围内服务多个群。切换群不意味着切换主机。
- 一个工作项只有一个当前负责人，协作者有明确的子工作或调查边界。
- AI 执行会话必须绑定具体群和工作范围；通用私人会话默认不继承所有群的资料。
- 共享 AI 身份在不同群的执行相互隔离；暂停某群不能误停其在其他群的工作。
- 子工作按需生成，对用户默认折叠；完成条件必须包含必要子工作的结果。
- 普通日志、临时工具输出属于事件或证据，不自动变成待验收成果。
- 同一事实只有一份有效工作状态；群聊卡、成员状态和详情均从它及执行回执派生。

## 3. 工作怎样开始与结束

### 3.1 默认流程

1. 用户在群里描述目标，可带文件、图片、代码引用或日志。
2. 系统判断是在询问、讨论、汇报请求、调整已有工作，还是发起新工作。
3. 明确且已授权的请求创建工作记录，选择一个可用负责人，显示可纠正的接手回执。
4. 负责人补齐必要上下文，记录验收条件，开始执行；不阻塞的未知项自行调查。
5. 发现可以独立推进且收益明确的工作时，才增加协作者。
6. 进展从真实事件更新；需要用户决策时在群里显示具体问题与建议。
7. 提交成果、验证范围、结果和限制；按工作风险与预先约定完成验收。

例：用户说“登录偶尔超时，帮我修一下”。回执为“已接手：排查并修复登录超时，补充回归验证。负责人：小林”。仅在项目、权限或复现条件确实阻塞时追问。

“登录是不是该重写？”先分析，不视为重写授权。无法确定新消息针对哪项工作时，显示简短目标选择；不能静默改动无关工作。

### 3.2 授权与确认

- 日常查询、分析、已授权范围内的可逆修改按现有权限执行，不增加逐步批准流程。
- 跨项目访问、公开发布、生产影响、不可逆动作，沿用真实权限与确认机制。
- 目标歧义、明显改变范围或重大技术取舍才向用户提交决策。
- 用户可以明确选择“先提方案，等我同意再改”，该约束记录在工作项中。
- 确认记录绑定具体工作与方案版本；方案实质变化后，旧确认不能当作新授权。
- 模型的意图判断不构成权限依据；实际执行必须由服务端检查作用域与授权。

### 3.3 工作状态与完成条件

工作生命周期采用：待开始 → 进行中 → 待验收 → 已完成；另有受阻、失败、已取消。受阻必须说明原因和解除条件，失败必须保留已完成部分及恢复建议。

暂停是执行控制状态，不改写工作生命周期。例如“进行中／已暂停”保留恢复所需的信息，不把暂停伪装成失败。

自动完成适用于已有明确、可机器验证验收条件且风险允许的工作；涉及主观需求或重要取舍时交给用户验收。独立 AI 复核按风险引入。模型自述、讨论多数票、命令返回零都不单独等于验收通过。

成果至少包含：改了什么、对应版本或变更引用、验证方法和实际结果、未覆盖范围、剩余问题。拒绝验收后回到进行中，保留之前成果和反馈的关联。

## 4. 多 AI 怎样协作

| 情况 | 组织方式 |
|---|---|
| 明确的小修复 | 一个负责人执行并验证 |
| 原因未知，存在独立假设 | 负责人按需邀请独立调查，结论附证据 |
| 重要方案选择 | 最多 1–3 个相关成员提出有区分度的方案，由负责人归纳建议 |
| 可拆分实现 | 明确接口、文件或模块边界后并行 |
| 高风险变更 | 执行与复核分开；按权限由人决定关键操作 |

协作规则：

- 增加成员必须说明要解决的未知或可独立产出；没有明确增益时继续单 AI。
- 候选方案有可区分的验证方法；优先跑最小实验，无法验证的取舍明确交给人。
- 负责人负责集成与收尾，不因邀请协作者转移最终责任。
- 并行代码修改使用隔离工作区或明确写入边界，集成后重新验证组合结果。
- 并发、模型开销和讨论轮次受项目预算约束；达到预算时汇报进度与建议，不自动扩张。
- 真人只有明确接受后才算接手；“邀请已发送”和“已开始工作”分开显示。
- 临时 AI 结束执行后可以释放资源，工作记录和交付成果仍可接续。

## 5. 信息传递与上下文

### 5.1 工作记录是共同依据

每项工作保存目标、验收条件、有效约束、负责人、协作者边界、决定与版本、事实与来源、进度与下一步、相关环境及成果引用。

聊天负责交流，工作记录负责保持当前有效状态。摘要必须保留原消息或证据引用；推测与事实分开。新约束替代旧约束时记录修订，不能同时给执行者两个互相冲突的版本。

每个 AI 接收与职责相关的工作上下文，并能按权限读取原始证据，不默认读完整个群或其他群的历史。工作交接包含未完成项、环境位置、已验证内容与风险。

### 5.2 @ 与消息语义

| 输入 | 行为 |
|---|---|
| @小林 到哪了？ | 面向小林的汇报请求，不新建工作 |
| @小林 先别改，看看日志 | 更新相关工作约束，并对已执行部分如实回执 |
| @小林 修复这个问题 | 有权限且目标明确时由小林负责 |
| @all 明天统一检查接口兼容性 | 全群可见的通知，不让每个 AI 立即各做一遍 |
| @all 各自给出接口方案 | 显式请求成员回应；AI 调用受可用性和预算约束，展示实际覆盖范围 |

@ 只决定接收对象；消息内容决定意图，服务端决定权限。广播不能隐式生成多个重复执行者。成员重名时选择器使用稳定身份，不依赖显示名作为投递地址。

### 5.3 群聊、私聊和暂停中的消息

- 群聊中的关键决定写入关联工作；细粒度工具过程留在执行会话。
- 在绑定群工作的成员对话里，影响该工作的约束同步到工作记录，界面明确标注此对话关联工作。
- 私人对话默认私有。把私人内容引入群工作前，允许用户审阅要共享的摘要，不能自动公开全文。
- 暂停中的群消息仍保存且真人可见；针对暂停 AI 的请求标记为等待处理。
- 不依赖模型的进度查询可从状态快照直接返回，注明更新时间。
- 待处理请求保留原文、目标、顺序、修订和处理回执；恢复时先处理撤销与替代关系，失效请求不得执行。
- 不按消息数量自动摘要重放。可合并冗余通知，不能丢弃有效约束；存在冲突再请用户决定。
- 投递区分已记录、待投递、已送达、已接收及失败；重试幂等，不能把重复投递变成重复工作。

## 6. 暂停、继续与结束

### 6.1 作用域与入口

- 群顶部按钮“暂停全部 AI”：暂停当前群的 AI 执行与新派发，对真人只通知。
- 成员行有常驻、可键盘操作的“暂停／继续”入口：控制该 AI 在当前群的全部执行。
- 工作卡可以暂停该项工作及其下属执行。
- 多群成员的全局停止放在成员管理中，明确列出影响范围，不作为群聊按钮默认语义。
- 群暂停优先于单成员恢复；恢复群不会清除之前独立设置的成员或工作暂停。

### 6.2 可确认的执行控制

控制状态为：可运行、暂停中、已暂停。界面分别显示控制意图与真实执行确认。

按下暂停后先持久化控制闸门，停止新工作派发、自动唤醒与后续模型调用；向正在运行的执行器发出暂停请求，在可确认的工具或模型边界停止并保存进度。安全边界不是承诺让整项任务跑完。

尚有在途调用、工具进程或未确认远端时显示“暂停中”，列出未确认项和最近状态。只有受控执行全部确认停下后显示“已暂停”。断网不能被当作已暂停。

已发出的外部操作可能无法撤回，运行中的调用仍可能计费。需要强制停止时提供“立即中止”，说明可能产生部分结果；中止也必须依据执行回执展示结果。

暂停期间不创建新的讨论、孵化、重派或自动接手。控制通道、状态同步和必要租约维护继续工作，避免暂停被误判成失联；讨论业务计时冻结，远端真实连接超时继续记录。

恢复时重新检查权限、环境、任务版本、已发生的外部效果和待处理指令，从最近可恢复进度继续。不盲目重放非幂等工具调用，不承诺恢复到同一条机器指令。

暂停、恢复、完成并发发生时，以工作修订和控制版本校验，已完成或取消的工作不得被恢复消息重新启动。

### 6.3 离线、取消、退出与删除

| 动作或状态 | 语义 |
|---|---|
| 离线 | 暂时无法通信；执行是否停止可能未知 |
| 取消工作 | 终止该工作后续执行，保留已有结果与事件 |
| 移出成员 | 撤销其当前群访问与派发资格，先处理其未完成责任 |
| 退出群 | 当前人退出协作，交接其工作；不影响其他群 |
| 解散群 | 结束整个协作空间，列出运行中工作与成果保留策略后确认 |
| 删除 AI（真杀） | 停止并删除 AI 身份及其专属会话、记忆，展示具体范围并确认；不是隐藏或软退出 |

共享工作、共享成果和审计记录不属于 AI 专属记忆，删除 AI 时保留其归属引用。尚未确认远端停止或删除时显示处理未完成；私有内容清除与共享记录保留范围在删除界面明确列出。

## 7. 交互设计

### 7.1 主界面

沿用现有 newbee 的视觉、消息卡、工具输出和输入组件。默认两栏，不强制常驻第三栏。

```text
左侧                              群聊
──────────────────────────────    ─────────────────────────────────────
[蜂群：newbee 开发 ▾]              newbee 开发   2 项进行中 [暂停全部 AI]
群聊                              [需要你决定 1] [查看工作 3]

成员                              你：登录偶尔超时，帮我修一下。
小林  运行登录回归测试  刚刚 [Ⅱ]   小林：已接手，先排查并补回归验证。
小周  等待接口约定确认       [Ⅱ]   [登录超时 · 小林 · 进行中 · 查看]
小陈  已暂停 · 缓存排查      [▶]
同事  处理接口文档（本人汇报）      ……关键进展、讨论、决定与成果……

[邀请成员]                        [附件] 输入消息，@ 指定成员     [发送]
```

头像点击进入该成员对话空间；暂停按钮有独立点击目标、可访问名称和触屏入口，不藏在悬停里。成员多时可搜索或折叠空闲成员，默认优先显示需要处理和正在工作的成员。

顶部工作入口打开按工作组织的抽屉，不创建第二个命令输入框。顺序为需要你处理、受阻、进行中、暂停、最近完成；工具详情通过工作卡或成员会话深入。

### 7.2 成员对话空间

点击成员后，左侧变为“返回蜂群”、成员信息、“新建对话”和历史会话列表；中央保留原有 AI 输出与工具展示。

- 保留模型、思考强度、附件上传、文件拖拽和粘贴功能；群聊不显示全局思考强度。
- 默认打开与当前工作关联的会话；新建对话明确显示是否关联群工作，允许私人对话。
- 对真人使用同样的会话导航，但不显示模型设置、工具执行控制或 AI 暂停按钮。
- 返回蜂群恢复此前位置；切换群或会话不丢输入草稿和附件。
- 模型与思考强度沿用个人 AI 会话设置，群内自动选用项目默认值，需要时才在成员设置调整。

### 7.3 默认可见的活动

成员行显示“当前动作／工作名称＋更新时间”；多项工作显示主活动与其余数量，展开查看。进度来自执行事件、工作状态或真人主动汇报。

用户词表：空闲、处理中、等你决定、受阻、暂停中、已暂停、离线／状态未知。具体动作如“检查日志”“编辑文件”“运行测试”优先于泛化状态。

不展示未经证实的“思考中”、耗时估算或百分比。远端状态过期时显示最后更新时间与未知状态；真人活动注明来源为本人汇报。费用仅在有真实用量和价格依据时显示。

### 7.4 群内消息控制

群聊保留：接手回执、关键发现、范围变化、阻塞与决定、暂停控制回执、成果。连续工具步骤合并为可展开进展，完整输出仍在执行会话可查。

工作卡显示目标、负责人、实际状态、最近活动，提供查看、暂停／继续及当前需要的操作。验收卡突出成果引用、验证覆盖、限制和通过／需修改。

输入框保留一个。@ 选择器显示身份、类型和可用状态，支持键盘；附件入口常驻。空白群给少量可点击示例，例如“排查一个问题”“开发一个功能”，点击填入可编辑文本，不直接执行。

## 8. 极简配置与跨主机协作

首次本地使用：选择或识别当前项目，复用已有模型凭据与工具环境，自动建立本地 Garden 和一个可工作的 AI。自动化不能绕过凭据缺失、目录权限或首次授权。

加入远端：邀请链接或码 → 登录或确认身份 → 明确项目访问范围 → 系统检测连接和能力。自动发现不等于自动信任，不自动暴露本地目录、密钥或私人会话。

日常只需切换蜂群。管理员可在设置中管理成员权限、项目默认模型、并发与费用预算、Garden 可用性；普通用户不配置节点地址、路由或内部阈值。

跨主机要求：

- 通信与业务工作身份分离，工作 ID、消息 ID 和修订可跨重试识别。
- 每项工作有唯一的状态写入权威和版本校验；不在同一版本上接受两个负责人。
- 断网时不盲目接管可能仍在远端运行的修改，先确认执行权与副作用。
- 附件按权限复制或传递可访问引用，不把发送端本地路径当作远端可读文件。
- 成果引用包含环境和版本，验收方能够实际读取并验证。
- 重连后先同步控制与工作修订，再恢复派发；旧暂停或旧恢复消息不能覆盖更新控制。

## 9. 完整使用场景与验收要求

| 场景 | 预期行为 |
|---|---|
| 群里说“修复登录超时” | 一项工作、一位负责人、一个可见接手回执；范围明确时直接调查 |
| 说“要不要重写登录” | 先分析，不授权即重写 |
| 要求先出 1–3 个方案 | 少量相关成员提供可区分方案，负责人汇总建议，等待约定批准 |
| @负责人询问进度 | 返回真实活动与时间，不创建重复工作 |
| @all 通知 | 全群可见，不自动让所有 AI 开始重复执行 |
| 暂停一个 AI，再暂停和恢复群 | 该 AI 仍保持独立暂停，其他符合条件的执行继续 |
| 暂停时远端失联 | 显示暂停中和未确认成员，不显示全部已停 |
| 暂停期间说“别改客户端，优先服务端” | 记录有效新约束，恢复前应用，不重放过时客户端指令 |
| 同一 AI 参与两个群 | 当前群暂停不影响另一个群，也不泄漏上下文 |
| 私聊改变关联工作要求 | 明确同步工作约束；私人对话内容未经审阅不公开 |
| 中断或更换 AI | 从工作记录交接，保留证据与未完成项 |
| 重复投递或重连 | 不重复创建工作，不重复执行非幂等外部动作 |
| 多 AI 并行修改 | 隔离写入，集成后验证最终组合版本 |
| AI 提交成果 | 展示变更与实际验证范围，未验证部分明确可见 |
| 删除 AI 或退出群 | 明确影响范围，处理未完成责任，不波及其他成员与群 |

## 10. 实施顺序与旧设计替换

### 10.1 先做一条可交付链路

1. 统一工作记录、负责人、上下文版本与成果证据；保留原有 Session 执行能力。
2. 群聊接手与进度卡、成员真实活动、头像进入原有会话；打通单 AI 完成与验收。
3. 实现群／成员／工作暂停的持久闸门、执行确认、待处理指令和恢复检查。
4. 接入跨主机控制回执、重试去重、断线恢复和附件访问验证。
5. 在单 AI 链路稳定后增加按需调查、并行与独立复核。

### 10.2 既有模块处理方向

| 既有设计或实现 | v2 处理 |
|---|---|
| Colony / Bee / Task / Honey / Session | 保留可复用实体，补齐身份与会话分离、责任与修订、证据及权限约束 |
| Queen 固定为一个人 | 改为管理员、成员和工作决策权限，不绑定生物角色 |
| 刺激强度、阈值与信号系统 | 从产品主流程移除；确有收益的调度策略留作内部实现 |
| 全员自动讨论、孵化、逐项批准 | 改为按需协作和现有授权内执行 |
| 群聊与工作轨迹双命令入口 | 群聊和明确按钮发出意图，轨迹只读 |
| Bee 等同会话 | 稳定身份关联多会话，工作可跨会话交接 |
| 一切工具输出都算 Honey | 交付成果与过程证据分开 |
| best-effort 投递即视为完成 | 引入实际回执、幂等与可见失败 |
| 旧 HTML 原型和实现说明 | 标记历史状态，不能据此声称 v2 已实现 |

迁移需保留原有会话、附件、成果和身份引用。先建立旧 ID 与新语义映射、迁移预览和回退方式，再切换写入入口；迁移验证完成前不删除旧数据或在两个后端同时派发同一工作。

## 11. 如何判断值得做

用真实的小修复、新功能、跨模块变更，对比现有单 AI 工作方式与本设计；记录任务规模、模型配置、环境及人工验收标准。重复使用同一任务须控制已有答案与缓存影响，不能用演示消息证明效率提升。

指标：提出目标到验证通过的总耗时、用户主动操作时间及干预次数、首次验收通过率、返工和缺陷、模型用量与费用、重复劳动和协作冲突。

通过原则：质量与权限边界不能退化；明确小任务不被强制增加讨论及确认；复杂任务的协作收益需超过协调成本。没有基线和对照前，只描述预期收益，不承诺效率提升比例。

文档验收与功能验收分开：本版替换完成仅表示设计统一；功能交付仍须覆盖第 9 节的场景，并回归原有 AI 对话、附件、拖拽、粘贴、模型选择和思考强度交互。
