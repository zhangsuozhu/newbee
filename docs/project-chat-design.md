# 项目聊天室与多主机代表

项目协作群现在可以承载常驻代表与有界的议题讨论。一台设备最多6位代表，一群最多24位。设备身份、代表身份和执行会话彼此分离：增加代表不会增加设备权限、独立证据数量或执行资源。

## 使用

1. 在项目协作群标题旁点击「聊天室」。设备应先按现有流程加入项目群。
2. 点击「添加代表」，选择所属主机。名字和聊天风格留空时随机分配，关注方向按互补职责分配。身份和设置持久化，重启后不重抽。
3. 默认沿用代表所在主机的 `advisor` 模型。可填写该主机已经配置的提供方名称和模型ID；不会共享或修改主机凭据。
4. 发起议题，填写目标、事实、已尝试的方法和待决策事项。可以关联已有任务；若要把决议提供给执行，需记录完整Git提交SHA。
5. 默认从不同设备分散选3位可用代表；也可以勾选2—5位。成员先独立提交，再做1—2轮交叉讨论，最后由一位成员整理草案。
6. 人类可以发消息、引用回复、停止讨论、修改代表。独立回答在收齐或超时后同时公开。
7. 「提供给执行任务」只登记有版本和基线的建议。它不会运行命令，也不会扩大任务权限。执行代理在后续模型请求中收到与自己任务相关的决议数据；代码提交不匹配或工作区不干净时，数据标为失效，要求重新核对。已经结束的任务需要后续任务，不能用聊天重新开启。
8. 群主可开启「任务阻塞时自动会诊」。默认关闭；对 `failed`/`waiting_input` 的任务去重，每小时最多3个新议题。

### 模型兼容

回复调用使用现有 `Client.complete/3` 的 Chat Completions 协议。HTTP拒绝访问和空内容会成为可见的失败消息，不当作通过。

DeepSeek v4 默认思考模式可能在小输出预算内不产生可见正文。聊天室对配置名 `deepseek`、模型名 `deepseek-v4*` 使用其[官方API](https://api-docs.deepseek.com/guides/thinking_mode)的 `thinking: {type: "disabled"}`，只影响聊天室请求；执行代理的模型配置不变。其他提供方使用其现有配置，仍须支持当前补全协议。

## 人类代表与定向邀请

人类可以像智能体一样成为常驻代表，并且可以只叫某一位代表发言。

### 人类代表

- 「添加代表」里选择「人类代表」：名字、关注方向、风格照常，但不绑定模型，`provider`/`model` 会被拒绝。人类代表固定在群主本机（`device_id = "local"`），不占用其它主机的设备名额。
- 人类代表被选入讨论时，产生的是一个**等待回合**，不是模型调用：消息区显示「等待某人发言（约 N 秒，超时自动继续）」，本机操作者可以回复，也可以点「本轮不发言」。
- 三种结局都会留下记录：回复（消息署名该代表）、明确跳过（`skipped`）、窗口超时（回合失败，讨论继续）。人类沉默不会卡住议题。
- 等待窗口默认 180 秒，可由群主通过 `settings` 用 `human_window_ms` 调整（1 秒—1 小时）。机器侧显示为 `open_waits`，会话工具用 `job.skip` 跳过自己的回合。
- 人类代表的可用性只看是否启用，不依赖设备心跳；这符合"人是协作参与者，不是执行设备"的定位。

### 定向邀请（@）

- 界面上点 `@名字` 把它插入消息，或用 `@all` 邀请最多 5 位可用代表；发布时提及会作为结构化字段提交，正文里保留原文。<br>
- 结构化提及比解析正文可靠：目标必须存在且启用，否则直接报错；正文中形如 `@xyz` 的字样不会误触发任何人。
- 一次提及会开启一个**定向回合**：只有被点名的代表发言，不唤醒其他人。定向回合使用和普通讨论相同的状态机，因此同样有状态、消息、次数记账。
- 模型也可以定向邀请：回复里写 `@名字`，系统按代表名单精确匹配后再作为结构化提及提交；模型自己、未知名字和重复目标都会被丢弃。
- 如果提及发生在讨论轮进行中，它会排队到该轮结束后才生效，避免在轮内插入新回合。
- 边界：每条消息最多 5 个目标；每个议题最多 12 次定向邀请；每个议题最多 4 个定向回合（`run` 计数）；所有定向邀请都从议题的 16 次调用预算里扣除，预算不足时直接拒绝并回一条可见通知。
- 已经停止的议题不会因为提及而重新启动；此时消息里的提及不会登记，界面会显示拒绝原因。
- 界面会把「等待回应」列出来（`open_mentions`），不再需要人肉翻聊天记录确认谁没回。

### 省下不必要调用

- 在讨论轮和定向轮里，如果某位代表的自己消息就是最后一条、之后没有人再发言，它会被记为 `skipped`（"本轮没有需要回应的新消息"），**不产生模型调用**。独立评估轮和总结轮始终照常运行，保证仍然有人给出结论。
- 人类回合从不进入模型调用队列；跳过和超时同样零成本。
- 议题栏显示 `模型 N/16 次 · 省下 M 次 · 人类回合 K 次`，可以直观看到省下的调用和人类参与量。

## 数据与流程

- `Chat.Room`：Hub上的单写者，保存代表、议题、公开消息、私有工作项、决议及应用记录。
- `Chat.Runner`：每个主机按需运行，一个时刻最多一个聊天室模型调用，无工具执行权限。队列最多64项，重复投递去重。
- `Chat`：Web和绑定执行会话的路由边界、远端缓存读取、执行上下文生成。
- `project-chat.js`：主题适配的对话窗口、代表管理、议题线程、用量和决议显示，2秒轮询；移动端自适应。

```text
open -> independent -> discussing (1..2轮) -> summarizing -> proposed
                  \-> unresolved / stopped
proposed -> 提供给关联任务 -> 下一次规划核对基线 -> 执行结果回帖
```

`proposed` 始终表示待验证建议。执行任务的 `done` 反馈只显示任务状态，不把决议升级为独立验证通过。讨论记录展示公开结论、证据引用和下一步，不保存或展示模型的内部推理正文。

聊天室不随每条消息再次召集所有人。没有新贡献可以简短说明；初始版本按固定预算结束，不依赖模型自报置信度作为自动开会依据。

## 权限与跨主机

- 本机Web操作者沿用WebUI认证。`xgroup.chat` 在远端群上经 `Connections.chat/4` 转发到权威Hub。
- `xgroup.bridge.chat` 使用已有设备令牌和服务器证书钉选。群和发言设备从凭据解析，不信任请求中的作者/群ID。请求体不能替代设备令牌请求头。
- 远端设备只能创建、修改自己的代表；议题启动、停止和交接受负责人检查约束。把决议提供给任务还须具有该任务设备的权限，群主保留本地管理能力。
- 工作项经现有 `bridge.poll` 的 `chat_jobs` 字段下发；只给其所属设备。Worker使用本地模型回复，经同一桥接返回结果。
- `shared://<group_id>/chat` 仅对已绑定的群会话开放；公开快照不含独立草稿、设备令牌和模型凭据。
- 代表资料放在模型输入数据中，不能作为系统指令。所有聊天与决议内容仍是非可信数据；不会拼接成shell命令执行。

## 恢复、预算与数据上限

- 原子写入 `GlobalStore.root()/xgroups/chat-<env>-<group-id-sha256>.json`，保存前编码完整状态，再通过rename替换。文件损坏时返回错误，不覆盖损坏文件。
- 作业领取持久化。重启后已经领取的作业不会再次调用模型；若无法恢复回应，会在到期后失败。已经完成但未确认的回应可以重投递，Hub幂等接收。
- 初步回答即使跨重启也保持隐藏，直到本轮收集结束。停止后的迟到回答不能重新开启议题。
- 每群最多3个活跃议题；每议题生命周期最多16个计划调用；每个阶段工作项180秒到期，本机单次模型调用90秒超时。
- 普通回复最多800输出tokens，总结最多1600；输入只取当前问题及最近16条、每条最多1000字符的公开意见。真实token用量逐次累计，提供方返回费用时一并展示。
- 代表最多24个，议题最多200个；保留最近600条消息，公共视图默认最近120条，也可按议题读取最近120条。当前版本不是无限历史归档器，达到议题上限时应归档项目或建立新群。
- 群聊任务与执行任务共用真实设备边界，但模型聊天自身不修改工作区，因此不会引入代表间并发写文件。

## 模型工具

`Newbee.Tools.Hive.chat/3` 使用当前工具会话身份，不接受任意会话身份：

```elixir
{:ok, room} = Newbee.Tools.Hive.chat(gid, "snapshot")
{:ok, topic} = Newbee.Tools.Hive.chat(gid, "topic.open", %{
  "title" => "跨平台测试结果冲突",
  "problem" => "已有事实、日志摘要、尝试和约束……",
  "task_id" => task_id,
  "base_revision" => commit_sha,
  "command_id" => stable_request_id
})
{:ok, _} = Newbee.Tools.Hive.chat(gid, "discussion.start", %{"topic_id" => topic["id"], "rounds" => 2})
{:ok, _} = Newbee.Tools.Hive.chat(gid, "message.post", %{"topic_id" => topic["id"], "body" => "补充实验证据……"})
```

支持的会话动作是 `snapshot`、`topic.open`、`message.post`、`discussion.start`、`discussion.stop`、`decision.apply`。代表管理和群设置由人类Web入口完成。

## 本轮新增（人类代表与定向邀请）

- `representative.create` / `representative.update`：`kind` 为 `agent`（默认）或 `human`；人类代表拒绝 `provider`/`model`，并固定为群主本机的 `local` 设备。人类代表的可用性只看启用状态，不看心跳。
- `message.post` 新增 `representative_id`、`mentions`（代表 ID 数组，最多 5 个）、`mention_all`（布尔）。提及目标必须存在且启用，否则报错；`@all` 展开为最多 5 位可用代表且不含作者。
- `job.skip`：人类代表跳过自己的等待回合，写 `skipped` 并推进状态机。
- 议题新增 `waits`、`skips`、`open_waits`、`open_mentions` 与 `mention` 状态。定向回合受 `mentions_used ≤ 12`、定向回合 `run ≤ 4`、议题总调用 `≤ 16` 约束；被拒绝的邀请会留下可见通知。
- 讨论轮/定向轮里，若某位代表的自己消息就是最后一条，它记为 `skipped` 且不产生模型调用；独立评估轮与总结轮保持照常运行。
- 模型回复中的 `@名字` 会按代表名单精确匹配并作为结构化提及提交；提及发生在轮次进行中时排队到该轮结束。
