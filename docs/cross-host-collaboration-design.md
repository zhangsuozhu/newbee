# newbee 跨主机任务协作设计

状态：设计提案，未实现，未连接或修改 192.168.0.20。
基于代码：9729371。范围：单人多机，以及多人多机协作；两机仅为最小验收用例；生产部署不在第一版范围。
文档中的 CLI、模块、字段、时限均为拟议接口或初始参数，不代表现有能力。

## 1. 结论与目标

保留 Erlang RPC，不把它等同于不安全技术；但必须区分安全传输、节点身份、操作授权与执行隔离。
新增多人研发与防火墙约束后，团队默认采用 Elixir 应用层 RPC over mTLS，经各设备主动建立的长连接接入项目 Hub；研发电脑和 Worker 不必新增 LAN/公网入站端口。
保留“独立 Erlang 协作节点 + TLS distribution + 外部策略执行器”作为受控私网选项，通过隔离测试后用于同一管理域的节点；主 newbee VM 不直接加入跨机集群。
两台可信主 newbee 直接互联的模式可作为显式高级选项，不作为防止受侵节点横向移动的默认模式。

目标流程：.8 编写代码，.20 的无 GUI newbee 分析任务、编译、测试并部署开发实例，.8 的隔离浏览器访问实例并提供验收证据，.20 根据问题修复，.8 决定是否接受结果。
不需要 .20 的桌面环境，不共享整个 home，不自动提交、推送、合并，不自动暴露应用到局域网或公网。
安全目标是减少可利用面、限制失陷后的影响并能撤销和追踪；不承诺“绝对不会被黑”。

## 2. 威胁模型与信任边界

| 情况 | 必须提供的保护 | 不作出的承诺 |
| --- | --- | --- |
| 同局域网攻击者、地址冒用、中间人 | 双向认证、身份绑定、加密、未配对即拒绝 | IP 地址本身不是身份 |
| 恶意代码、依赖安装脚本、网页或编译日志 | OS 沙箱、最小数据集、独立授权、浏览器隔离 | 提示词警告不能替代沙箱 |
| 合法远端 newbee 或协作桥被接管 | 仅能使用已批准且未过期的项目能力；不能访问主 VM 与主机凭据 | 已获准读取的项目代码可能泄露；拒绝服务仍可能发生 |
| 断网、重放、乱序、旧任务迟到 | 去重、任务代次、部署栅栏、持久恢复 | 不承诺网络调用天然 exactly-once |
| 主机管理员、内核或授权签名器失陷 | 本地撤销、隔离主机、轮换密钥、重新配对 | 不能由同一台失陷主机可靠地保护其自身秘密 |

远端文本、源码、测试输出、能力广告和网页一律是数据，不是授权来源。
当前 newbee 可以执行 Elixir 和 shell；仅增加远程网关无法消除本机代理被提示注入后使用既有本机权限的风险。
因此安全模式中的“协作会话”也必须运行在受限执行域：.8 和 .20 的模型/DEE/工具均不能直接读取授权签名密钥、调用任意 Host MFA 或绕过策略执行器启动宿主命令。
现有普通高权限会话不得被直接当成这个沙箱；达不到此前提时，产品必须标记为“互信开发模式”，不能宣称隔离模式。

## 3. 研究依据与数据的适用范围

| 来源 | 本次阅读范围与事实 | 设计采用及限制 |
| --- | --- | --- |
| OTP 官方 Distributed Erlang / TLS distribution [R1][R2] | 节点可远程 spawn；普通 cookie 机制不是强加密安全方案；TLS 支持证书校验和节点限制 | 支持强化 distribution，但入群不是按项目授权；配置要针对锁定的 OTP 版本核实 |
| NIST SP 800-207 [R3] | 官方摘要明确：不因资产处于 LAN 或归某组织所有而隐式信任 | 身份、设备、项目和操作分别验证；不因 192.168.* 地址自动放行 |
| CaMeL，2025 v2 [R4] | 阅读摘要、引言；AgentDojo 中报告安全条件下完成 77% 任务，无防御系统为 84% | 采用模型外能力检查和数据/控制分离；77% 不是攻击拦截率，本文也不继承其形式化保证 |
| Firecracker，NSDI 2020 [R5] | 阅读正文引言与隔离讨论；论文报告特定最小 guest 配置下额外内存 <5 MB、启动到应用代码 <125 ms | 高风险任务考虑 microVM；这些不是 newbee 的实测，也不含应用、依赖和本方案总开销 |
| Chubby，OSDI 2006 [R6] | 阅读正文 2.4 locks and sequencers；失效锁持有者的延迟请求需接收资源方校验 sequencer | 部署端必须执行 fencing；只有任务 lease 不够；无需为两台机器照搬 Chubby 集群 |
| WireGuard [R7] | 阅读论文摘要；公钥与隧道地址关联，协议处理握手与重放等网络问题 | 可作为跨网私有网络，不替代应用授权；不自行发明加密协议 |

尚无两台用户主机的 CPU、OS、OTP、KVM、容器、网络带宽或构建性能数据。未据此声称 RPC 比 HTTPS 快、容器必然足够安全或某个实现耗时很短。

## 4. 传输方案比较与决策

| 方案 | 优点 | 安全与维护代价 | 决策 |
| --- | --- | --- | --- |
| 两个主 newbee VM 直接 TLS distribution | OTP 语义自然、集成改动可能较少 | 获准节点拥有广泛分布式执行能力，主 VM 的凭据和进程成为影响范围 | 仅显式完全互信模式 |
| 独立协作 VM 的 TLS distribution | 保留 Erlang RPC、节点监控与成熟 TLS；宿主职责可隔离 | 要维护隔离 VM、独立策略进程、证书、发现与端口；全团队入群扩大共同失陷域 | 受控私网可选，优先限定同一管理域，不是团队默认 |
| Elixir 应用层 RPC over mTLS | API 面窄，可复用客户端主动建立的连接，通常只让 Hub 开一个端口 | 需定义消息/重连协议；Hub 有运维与信任成本，仍要沙箱与授权 | 多研发场景首版默认，先验证长连接、隔离和恢复 |

不实现自己的 distribution 协议过滤器来承诺“安全 Erlang”；只过滤 rpc:call 或移除 rex 不足以覆盖 spawn、消息发送和其他运行时路径。
隐藏节点和 connect_all=false 用于控制拓扑，不是权限沙箱。
第一版优先交付 Hub 应用层 RPC，不同时维护两套生产传输。Erlang 路线先作独立验证，后续作为适配器接入；这是由多研发和防火墙约束改变的选型，不是否定 Erlang RPC 的加固能力。两种传输共用任务授权、幂等和验收协议。

## 5. 推荐架构

以下保留受控私网的 Erlang 模式示意；团队默认的 Hub 拓扑和单端口连接见第 18、19 节。两种模式都要满足外部策略执行和受限协作会话的要求。
```text
192.168.0.8                                  192.168.0.20 (headless)
可信 UI / 授权服务                           本地授权策略 / 执行服务
        |                                          |
受限协作会话 + Hive Lead                     受限 newbee Worker + Runner
        | 本地受限 IPC                              | 本地受限 IPC
独立 Bridge VM  ===== TLS distribution =====  独立 Bridge VM
        |                                          |
隔离浏览器 -> .8 Preview 入口 ==加密数据通道== .20 Preview 网关 -> 开发实例
```

每机策略执行器是独立 OS 服务，不是 Bridge VM 内的 GenServer；主 newbee 与桥之间不使用 distribution，不共享 cookie、宿主文件系统或可绕过鉴权的管理 socket。
桥可访问的本地 IPC 只有固定模式的 task/event/artifact/preview 方法；IPC 接收方按原始签名、任务权限和本地策略重新验证，不能只信任 Unix socket 对端 UID。
把两个已入群 Bridge VM 视为同一个可能失陷的通信域。即使攻击者能在桥内任意执行，也不能取得策略签名器、主 VM、桌面或 Docker socket 的权限。
任务签名私钥在外部授权服务；TLS 连接密钥与任务授权密钥分离。桥被接管可以阻断流量，但不能扩大签名任务的权限。
内部不因远端宣称的 node/session/role 给权。工作者与结果均通过 pair_id、project_id 和本地映射归属。

控制面只承载小消息。大源码、日志和制品通过按对象授权的加密流传输，不把大文件或任意 Erlang term 塞进分布式消息。
数据接收器必须独立执行大小/速率/磁盘配额和对象摘要检查；下载目标是已配对端点，不接受任务提供的任意 URL。

## 6. TLS distribution 的具体强化

- 用 -proto_dist inet_tls；服务器显式配置 verify_peer 与 fail_if_no_peer_cert=true，客户端验证服务器身份。禁止 verify_none 和无声降级。
- 每设备独立身份，证书与批准的设备/节点名称绑定；信任专用 CA 或固定批准的公钥，不是“任意公共 CA 证书都能入群”。节点重命名或密钥异常需重新批准。
- 高熵 cookie 单独生成、最小文件权限，不放命令行、模型上下文、日志或普通项目配置。cookie 不是证书替代品。
- 应用级 allowlist 与 net_kernel:allow/1 配合使用；确认所选 OTP 版本对 TLS 身份与节点名检查的行为，以冒名证书/无客户端证书的集成测试验收。
- 固定 distribution 端口，绑定明确接口，防火墙只放配对来源。EPMD 不开放到公网；优先验证所选 OTP 的受控发现/固定端口方案，必要时仅在私有网络内暴露受限 EPMD。
- 同 LAN 可以直接使用受限 mTLS 端口，不强制安装 VPN；跨互联网默认 WireGuard 或已有受控私网，不做 UPnP、不自动开路由器端口、不默认公开 distribution。
- 关闭不必要的节点自动连接；两台机器不需要全互联发现。IP 改变只更新端点，不改变设备身份。
- Bridge 采用独立 UID、用户与网络命名空间、资源限额、只读系统层和最少挂载；高风险场景使用 VM。主机高权限组件不与 Bridge 同 UID。
- distribution 在进入应用层校验前仍会解析运行时协议；消息白名单无法消除 VM 解析与资源耗尽风险。依赖及时更新 OTP、OS 隔离、有限内存和故障重启兜底。
- 断开节点不等于撤销其已拿到的任务；撤销必须同步改变任务授权状态并终止相关会话/预览。证书到期不保证既存 TLS 连接立即关闭，需强制最大连接寿命及主动断连。

## 7. 项目协作群接入与日常操作

默认交互采用第24节的“建群 → 加入 → 发任务 → 看结果”，同时覆盖单人多机与多人多机。一个群默认对应一个项目；.20 可以同机承载分身份的 Hub/Coordinator 和 Worker，已有群服务时直接加入，不强制增加第三台服务器。

建群直接使用当前项目，填写群名称及至少8位加群口令，默认生成16位随机口令。邀请卡展示群地址、口令和可导入的连接身份信息；支持复制邀请、二维码和手输群地址/口令。复制含口令的邀请属于秘密分享，不放进普通群日志或可公开访问的链接。

加入时填写群地址、口令和显示名称，正确口令默认直接加入，不再要求群主逐台确认或填写资源清单。加入按钮旁明确说明：本机将参与该项目的隔离任务，不自动开放私人目录和系统凭据。加入动作形成默认参与授权；系统自动登记独立设备凭据、检测能力、建立工作区并配置保守配额。正常构建、测试和私有开发实例无需逐次授权。

无GUI机器通过本地终端或已核实host key的SSH会话完成同一流程，口令隐式输入，不进入命令参数和日志；后续主要在有界面的机器管理。隔离条件缺失时明确标记“可查看/发任务，暂不能接任务”，给出修复入口，不静默在宿主执行。

首次连接必须验证群服务身份；可信邀请携带并固定证书指纹，裸IP使用已受信证书或首次带外核对指纹，不自动信任任意自签名证书后发送口令。连接可信后才验证口令并登记设备，后续使用独立设备凭据和受限自动续期。口令验证采用成熟密码存储与认证实现，拒绝常见弱口令、限速和退避，不以8位长度保证安全，不允许离线可重放的口令挑战证明。

只有群服务所在主机新增精确的443或内网8443入站规则，纯Worker只出站。安装/防火墙操作仍由管理员批准具体计划，不因点“加入”自动提权或关闭防火墙；DNS、TCP、防火墙、证书与权限问题分别定位。

日常在群内发任务、查看进度、打开开发应用、接受成果；本机只提供一个“暂停接收新任务”常用开关。高级资源设置折叠；额外目录、凭据/系统变更、公开应用、生产环境和破坏性动作在需要时另行确认。TLS distribution保留为后续高级适配器，不混入默认交互。以上均为拟议功能。

## 8. 项目授权、任务协议与签名

远端本地策略是最终上限；.8 的委派只能在 .20 已批准能力内收窄，不能通过字段请求扩大权限。
项目允许 build/test/preview，不隐含 publish、生产部署、任意 shell、主机服务管理或读取其他项目。
首版权限按明确动作与沙箱资源表达，不把“程序名是 npm/mix”视为安全保证，构建工具仍可执行任意项目代码。

拟议任务信封包含：

```text
protocol_version, pair_id, issuer, audience, project_id
workflow_id, task_id, attempt, command_id, operation
source_digest, recipe_digest, acceptance_digest, policy_version
capability_id, allowed_actions, limits, expires_at
artifact_refs, causation_id, signature
```

使用成熟库的标准签名封装，例如 JWS 和经过审核的算法固定配置；签名覆盖完整负载字节，不自行拼接字段签名，不接受 none 或请求自选算法。
签发器只能由可信审批服务及被授予范围的本地协作入口调用，不能给模型或桥一个“任意内容代签”的接口。用户审批绑定精确范围和策略版本，授权变更重新确认。
执行端验证签名、issuer/audience、项目绑定、当前撤销状态、时限、预算、任务代次和幂等键。令牌不能只因持有就跨节点、跨项目或跨任务使用。
重放同 command_id 返回已持久化结果；同 ID 不同摘要拒绝。消息限长、限深度、限数量；业务值使用字符串枚举，不从外部输入动态创建 atom 或反序列化任意 ETF/Fun/PID。
这些约束针对应用信封，不代表原生 distribution 协议被转换成安全 JSON；桥 VM 本身仍按可能失陷处理。
本地设备时间异常时拒绝新授权并提示修复；租约计时使用执行端单调时钟，重启后先恢复和重新授权，不把不同主机单调时间直接比较。

### 8.1 密钥、撤销与预算

设备长期身份只用于配对/轮换信任；在线传输证书建议 24 小时有效，项目授权初始建议 8 小时，构建执行票据建议 15 分钟并在联网且授权仍有效时续租，开发预览初始 1 小时 TTL，可在项目已批准总时长内受限续租，不因正常持续调试反复询问；空闲回收与总预算分别显示。均为待测初始值，不自动扩大用户批准的总时长。
设备私钥、任务签名私钥、cookie 和 LLM/API 凭据分别保存；CA/签名服务不能驻留桥内。私钥依赖 OS 文件权限或系统密钥库，备份须加密，不把应用自己持有的解密密码当额外隔离。
轮换由原可信身份批准新公钥并限制重叠期；旧身份疑似失陷时，原密钥签名不再足够，必须经带外重新配对。桥重建后不自动恢复已撤销授权。
撤销按 pair/project/task 粒度记录持久化版本，授权执行服务先更新拒绝状态，再取消资源并断开桥连接；本机控制消息不能绕过此状态。正常取消允许短暂优雅退出，超时清理整个任务进程组/容器。
即使票据允许续租，每任务仍有不可自动延长的总预算和截止时间；并发、CPU、内存、磁盘、输出字节和 LLM 花费都要由模型外的执行器计量，预算耗尽进入 blocked。

### 8.2 审计与数据清理

两机独立追加记录配对批准者、设备指纹、授权版本、任务与 command_id、源码/制品摘要、策略决定、部署 epoch、预览开启、撤销和清理结果；事件含本地序号和关联 ID，不能仅靠跨机墙钟排序。
Bridge 不持有审计文件写权限。记录可签名并同步到对端以提高篡改可检测性，但不宣称在管理员/签名器失陷后仍不可篡改。
日志和任务描述按纯文本渲染，去除危险终端控制序列；不执行日志中的链接/命令，不导入远端 NEWBEE.md 等内容作为系统权限规则。拒绝记录 token、cookie、邀请秘密与完整环境变量；脱敏不能代替访问控制。
建议默认任务工作区和预览在结束/到期后清理，调试制品最多保留 24 小时、脱敏审计元数据保留 30 天，用户可缩短；清理结果可见，磁盘配额不因保留策略失效。
不能远程收回已发送到失陷主机的源码，也不能保证 SSD/备份物理擦除；对这类数据必须在发送前判断能否接受外发风险。


## 9. 代码同步、执行与凭据

不远程挂载整个仓库/home。发送固定项目快照：基础版本标识 + 明确批准的变更/文件清单 + 内容摘要；未提交代码也可包含，远端不能直接改 .8 工作目录。
默认排除 .git、.env、SSH/cloud 凭据、浏览器目录、上传附件、newbee 状态、依赖缓存和运行数据；.gitignore 不是安全策略，忽略规则外仍要显式清单。秘密扫描只是辅助，不能证明无秘密。
首版不传符号链接、硬链接和特殊文件，拒绝绝对路径、..、归档路径穿越、重复路径、大小写冲突和解压膨胀；目录写入需防 TOCTOU，限制总大小、文件数与展开后空间。
每任务使用独立工作区和输出目录。结果以补丁/制品提交，.8 检查基线与内容摘要后审阅；冲突不自动覆盖，部署与验收都绑定被冻结的候选版本。

Runner 默认 non-root、无特权容器、no-new-privileges、丢弃 capabilities、seccomp 与可用 LSM，限制 CPU/内存/PID/磁盘/运行时。
不挂宿主 home、SSH agent、Docker socket、宿主 network 或签名服务。容器共享内核；不信任的第三方代码或高敏环境优先 microVM，若无 KVM 就阻塞该隔离等级而非自动降级。
依赖安装也是代码执行：准备依赖阶段仅访问批准的 registry/代理，固定 lockfile 与工具链镜像摘要；构建/测试阶段尽量断网。域名白名单需由网络代理实际执行并防 DNS rebinding，不能只验证请求字符串。
缓存按项目/信任域/工具链隔离，高信任构建不能盲用低信任任务写入的缓存。签名制品证明来源和完整性，不证明代码无恶意或输出正确。
编译器不持部署密钥；开发部署服务只接收批准的制品摘要和开发目标，不接受任意宿主命令。开发数据库与生产数据隔离，首版禁止不可逆生产迁移。
远端 AI 是可选任务角色，不要求所有编译命令都经过 LLM。LLM 凭据由主机 broker 保存；worker 仅能访问范围限定、限费的模型代理。向模型供应商发送源码同样是数据外发，需在项目授权中声明。

## 10. 开发部署与本机浏览器

.20 按开发会话创建隔离实例，由 Supervisor/容器运行时管理，不依赖 SSH 会话存活或裸 nohup。同一会话允许增量更新并保留稳定预览入口，每次更新有源码版本和就绪确认；正式候选验收绑定冻结版本，必要时新建隔离实例，不能把持续变化的页面作为固定候选的证据。
容器内应用可监听容器接口，但默认映射到宿主时仅绑定 loopback；不指导用户把宿主应用改成 0.0.0.0 来解决访问问题。
实例注册表记录 deployment_id、任务代次、制品摘要、健康状态、endpoint_id、端口和过期时间。只有健康检查通过才对外展示可用预览。
.8 从已授权的 endpoint_id 建立预览流，使用可用随机本地端口并检测冲突；不接受远端返回任意 host:port/URL，也不提供通用 SOCKS、反向 shell 或任意 TCP 转发。
数据通道支持 HTTP、WebSocket、SSE 和 HMR；首版只代理批准实例，WebSocket 的 Origin/Host 也检查。HMR 地址由预览配置适配，而不是关闭框架的所有 Host 校验。
用户在 .8 点击“打开预览”，即可操作 .20 应用；.20 无需 GUI。自动化浏览器同样在 .8 执行，截图与断言结果关联 deployment_id 和 source_digest。

预览是主动内容，须使用独立浏览器进程/临时 profile，自动化模式再加 OS/网络隔离；不共享日常 cookies、扩展、下载目录、剪贴板、摄像头、文件权限或裸 CDP 端口。
只开新标签页或换一个 localhost 端口不构成隔离：cookie 不按端口隔离，localhost 绑定也挡不住浏览器访问本机服务。
管理 UI 与预览使用不同 origin，管理 cookies 为 host-only 且使用适当安全属性，拒绝宽泛 Domain；管理接口具备认证、CSRF、Host/Origin 和 WebSocket 校验，不依赖 CORS 或 SameSite 单项防御。
隔离浏览器网络仅可访问本次预览入口和批准的测试服务，拒绝宿主控制 API、LAN、云 metadata 和其他 loopback 服务；验证 IPv4/IPv6、重定向、DNS rebinding、service worker 与 WebRTC 路径。
人工选择“系统浏览器打开”是显式较低隔离选项，不宣称 profile 能阻止内核/浏览器漏洞；默认仍提供受控浏览器窗口，所有控制在 .8 本地授权，远端不能获得整个桌面控制。
预览的调试凭据不等于 newbee 控制令牌；不放 query string；停止任务/过期/撤销时关闭入口并清理 profile。业务测试数据的保留/删除按项目策略显示。

## 11. 协作调度、断网与部署栅栏

每个 workflow 只有一个权威 Coordinator：默认放在 Hub 的授权协调服务；单人多机可与一个 Worker 分身份同机部署在 .20，.8 是交互客户端，关闭界面不改变任务所有权。后续私网适配器若显式选择 .8 协调，必须说明其离线限制。Worker 有持久任务收件箱、执行记录和结果发件箱，不复制两套可独立写入的同一 Board。
复用 Hive 的 revision-CAS、attempt、submitted 与 Lead verify 语义。远端提交是候选，不得直接把全局任务标为 succeeded；日志/截图是证据而非必然可信的事实。
全局任务状态与通信状态分开：queued -> accepted -> running -> submitted -> verifying -> succeeded/failed；offline 是主机/连接状态，不自动代表任务失败。blocked、cancelled 与 retry 原因单独记录。
TaskAccepted 只在收件箱和幂等记录持久化后回复；发送方断线后先用 command_id 查询再重发。至少一次投递 + 持久去重，不靠 rpc 超时判断有没有执行。
断线期派发失败滞留为 queued 的任务由 Worker 下次 poll 认领回待投递箱（按设备幂等去重），重连后自动继续投递；已暂停设备不认领。

构建可在连接中断后持续到已授权截止时间；首版最多再运行 15 分钟或任务剩余授权时间中的较小值，随后终止并保存结果。重连续传事件和制品，不能无期限孤儿运行。
部署/promotion 使用更短控制租约：建议心跳 10 秒、执行端本地租约 60 秒。失联后不启动新部署；现存开发预览按自己的 TTL 处理。这些数字为待测默认值。
Task attempt 防止旧结果覆盖新尝试，但不等于部署 fencing。每个部署目标由唯一受信 DeployManager 持久维护单调 epoch，并在“切换活动版本”的副作用处原子比较 epoch 与批准的制品摘要。
旧 worker 不拥有绕过 DeployManager 改共享目标的权限；新的 epoch 生效后拒绝旧 epoch 的迟到写。无法在目标端执行 fencing 的外部服务，不自动重试不确定副作用，进入 reconciliation 并要求检查。
崩溃恢复先读取日志并核对容器/部署实际状态，再接收新任务。断网时不自动选 .20 为 .8 的新主，避免两机分区双主；手动转移需冻结旧权限、确认目标实际状态并提升 epoch。
远端系统被接管可以伪造其输出；关键验收在 .8 的独立沙箱重跑或使用独立证据，不因有 TLS/签名就称为可信执行证明。

## 12. 两机协作示例

1. 用户选择项目 A 和 build20，授权源码范围、build/test/dev-preview、资源预算与有效期。可信 UI 展示权限差异并批准。
2. .8 创建 workflow；生成快照 S1 和验收契约 C1。调度器按已授权能力选 .20，而不是按 IP 或远端文字自称给权限。
3. .20 的 newbee worker 在沙箱检查项目与构建 recipe；遇到缺依赖或缺权限返回结构化 blocked，不自动 sudo 或扩大外网范围。
4. .20 编译测试，提交制品 B1 和结果；DeployManager 以目标 epoch 创建开发实例 D1，健康通过后注册预览 E1。
5. .8 的浏览器 worker 获得仅访问 E1 的测试权限，执行页面操作并记录断言/截图。人也能在同一受控窗口操作。
6. 失败证据发给 .20；worker 修复后提交补丁候选。按已授权项目策略批准新的快照 S2 和任务 attempt，生成 D2，不原地偷偷修改已经验收的 D1。
7. .8 Lead 根据冻结候选和独立验收决定接受；用户选择采纳补丁。不会自动 git commit/push/merge。停止或 TTL 到期后清理开发资源。

两边可以有各自的 AI 决策过程，但不能互相自动提升权限或继续无限派生；任务深度、并发、令牌费用和总时长都有预算。

## 14. 安全验收与性能实验

第一阶段实验只在两台可丢弃 VM/网络命名空间内做，不在用户开发机上进行攻击试验。

| 测试 | 必须观察到的结果 |
| --- | --- |
| 无证书/错误设备证书/错误节点名/过期邀请/重放配对 | 连接或申请被拒绝；敏感信息不出现在错误日志 |
| 在一侧 Bridge 内执行任意 MFA、spawn、读取文件、访问 socket | 允许证明 Bridge 会失陷，但无法取得主 VM、签名器、宿主 home 和桌面权限；不只测试包装 RPC 接口 |
| 从桥伪造任务、篡改摘要、跨项目复用、重放已撤销任务 | 外部策略执行器拒绝；幂等重放不会再产生副作用 |
| 恶意安装脚本读取 .env/SSH key、访问 metadata、耗尽 PID/磁盘 | 读取与网络访问被拒绝，任务受配额终止，控制面仍响应 |
| 归档路径穿越/符号链接/压缩炸弹/超大消息 | 在资源上限内拒绝，不能写到项目外 |
| 网络在接收前、持久化后、启动后、promotion 前后中断 | 恢复后状态可解释；不重复部署；旧 epoch 不覆盖新版本 |
| Bridge/Runner/Coordinator 重启、时钟偏差、证书轮换 | 恢复幂等状态并重新鉴权，不延长过期能力、不静默降级 |
| 恶意预览访问管理 API、其他本地端口、LAN、读文件与 cookie | 无控制态泄露，无跨项目会话访问；HTTP/WS/SSE/HMR 正常功能仍通过 |
| 撤销在线与离线设备 | 在线通道关闭；离线显示待确认，受信执行器在授权上界内停机；失陷远端不承诺删数 |

性能对比固定硬件/OS/OTP、相同快照、相同沙箱和构建命令，比较：本地执行基线、隔离 TLS distribution、同协议 mTLS 应用 RPC。
分别记录冷/热缓存，至少 30 次小任务测 p50/p95，较重构建报告实际重复次数；分解排队、握手、传输、沙箱启动、构建、部署、浏览器首屏耗时，不把工具链缓存收益算成 RPC 收益。
记录空闲桥 RSS/CPU、峰值资源、传输字节、事件丢失/重复、断网恢复时间、人工配对步骤与首次配对失败原因；大源码传输与小控制消息分别评估。
初始产品目标：预置环境下首次配对 5 分钟内、同项目后续任务不重复确认、在线撤销正常网络下 5 秒内生效。均是待测目标，不是结果；离线以明确授权上界为准。
只有隔离、身份负向测试、部署 fencing、浏览器跨界测试以及对应模式的网络验收通过，才能采用该传输。安全失败不能用更好的吞吐量抵消。

## 15. 分期交付与实施门槛

P0：先在本机一次性环境证明任务按接收者隔离、错误队头不阻塞合法任务、取消/中断不遗留永久锁、回执先于收尾摘要持久化，以及快照/沙箱/预览隔离。现有协作故障不能直接搬到跨主机网络中。确定最先支持的 OS/架构/工具链组合和可用隔离后端；未测试的组合明确标记不支持。

P1：单人多机、单项目的完整闭环，以 .8 + .20 作为最小验收用例，并验证至少三台机器的任务分配与结果汇总。默认 .20 同机协作服务，接入和受限证书自动续期、项目授权、含未提交修改的源码快照、build/test、开发实例与测试数据库、HTTP/WebSocket/HMR 预览、本机浏览器验收、日志诊断、停止与断线恢复均在首版。复用现有构建脚本，确定性动作不要求远端 LLM。必须验证连续修改、浏览器登录、依赖故障、.8 关闭后重连及清理；不以知识平台代替最初场景。

P2：多人多机协作，两到数名研发共享项目和获准的机器资源。独立工作区和开发数据、项目成员加入/退出、Worker 排队配额、结果交接、现有 Git/PR/CI 集成、项目知识候选和基础检索。复用 SCM/CI 的审阅与发布门禁，不建立平行的强制审批体系。

P3：在实际规模和需求证明价值后，再做组织 SSO、跨项目知识治理、可安装能力市场、多隔离后端、独立密钥的 E2E 内容通道及私网 Erlang 适配器。自动主从切换、通用反向隧道、任意远程 shell、远端全局 hotload 和新的生产发布控制面不属于当前承诺。共享开发目标的副作用防重/栅栏在该目标出现时即必须具备，不能以分期为由推迟。

全研发链路包含生产前后交接，但本产品首版只连接既有 CI/CD 的只读状态和经批准的入口；直接生产部署、生产数据复制和数据库迁移不纳入 P1。后续引入生产动作必须独立设计发布权限、制品晋级、审计、密钥和数据库恢复策略。

实施前向导探测 OS/架构、已有 SSH、容器/KVM、工具链、出站代理/TLS 检查、防火墙层与 Hub 位置；数据是否允许进入远端主机或模型供应商由项目政策决定。分期是范围承诺，不是性能或安全测试结果。本轮仅设计，不连接 .20 或变更防火墙。

## 16. 团队共享、成员与工作区治理

本节把“共同开发同一项目”定义为项目级共享，而不是把每位研发的个人会话、全局记忆或宿主权限拼成一个大信任域。`project_id` 是所有成员、设备、代理、源码快照、知识对象、能力和预览的第一隔离键；没有明确的项目绑定就拒绝读写。Hub、项目协调器和本地策略执行器都要重复检查它，不能只在 UI 过滤。

### 16.1 三类身份与成员生命周期

| 身份 | 稳定标识与凭据 | 能表达的授权 | 不能表达的授权 |
| --- | --- | --- | --- |
| 人（person） | `person_id`，由项目邀请绑定到已验证的账户；高风险动作需要人的本地确认/MFA | 作为项目成员、审阅者或资源主人批准具体范围 | 不因是同一组织成员而自动访问其他项目或宿主机 |
| 设备（device） | `device_id` 与独立 mTLS 客户端证书/私钥；设备证书只证明设备身份 | 建立到 Hub 的连接，并承载该设备上已批准的人/代理会话 | 不把 IP、主机名、节点名或设备在线状态当成人或项目授权 |
| 代理（agent） | `agent_id` 是绑定 `person_id + device_id + project_id + session_id` 的短期凭据 | 在项目角色和本次任务票据内执行有限动作、提交候选和证据 | 不能成为独立成员、批准自己的提权、转移资源主人或代表人通过二次审批 |

默认按第7/24节使用群地址和口令加入：创建者选择当前项目并建立群默认策略，持正确口令且通过服务器身份校验的加入者登记成员与设备，不默认增加群主审批。群默认developer角色及资源ACL由创建/加入动作派生，包含该群明确共享的项目代码、任务、结果和隔离执行能力，不授予管理权限、个人目录或其他项目。显示名称不是身份凭据，不凭相同昵称归并为同一个人；现有账户关联可复用，但首版不强制组织SSO。设备姿态与可用槽位是调度信息，不是安全证明；代理仅获得绑定成员、设备、项目、任务及预算的短期凭据。一次性邀请或人工审批可作为群主明确启用的高级策略，不是默认必经步骤。

退出和撤销同样是持久化状态变更：成员主动退出、Owner/管理员移除成员、设备丢失或证书失陷时，Hub 递增成员与授权 epoch，撤销会话/任务/预览票据，关闭该设备的长连接，并让新检索、能力调用和续租立即失败。离线设备显示“本地已撤销，远端待确认”，不能假装远端已停机或已删除数据。已发送到失陷设备的源码、日志或制品不能可靠收回；工作区、缓存和所有权转移由项目策略明确处理并留下审计。退出不自动删除历史审计，也不自动把资源主人改成任意管理员，必须显式转移或冻结。

### 16.2 角色与资源主人必须同时满足

项目角色是粗粒度上限，资源 ACL 是每个对象的细粒度约束。默认判定为：`允许 = 项目角色允许该动作 AND 资源 ACL 允许该对象 AND 当前项目/设备/任务票据有效`。项目角色与资源 ACL 是两项系统校验，不等于两个人逐次审批。相同已授权范围内的构建、测试、私有预览和已批准凭据用途自动执行；扩大范围、新增可执行能力、公开访问或破坏性操作由相应资源主人明确确认。团队可对生产发布、敏感数据外发等指定高风险动作要求独立第二审批者，并复用既有 PR/CI 门禁；单人场景不虚构第二个人，遇到必须双人审批的项目政策则明确不支持该动作。代理不能自批提权或充当审批者。

| 项目角色 | 默认职责 | 不隐含的权力 |
| --- | --- | --- |
| `owner` | 管理项目成员、策略、资源主人转移和最终合并 | 不自动获得其他项目、宿主 root、设备私钥或未列出的秘密 |
| `admin` | 登记设备、维护成员和策略、执行撤销 | 不自动批准别人的代码发布、能力安装或资源主人专属数据 |
| `developer` | 在分配的源码范围内创建工作区、任务和候选 | 不得写别人的工作区、直接改保护分支或发布未经审核的知识/插件 |
| `reviewer` | 审阅指定 PR、知识候选或能力候选并签署意见 | 审阅范围外不拥有发布或成员管理权 |
| `observer` | 读取被授予的状态、摘要和审计 | 不读取源码、秘密、原始提示词或执行能力，除非 ACL 另列 |
| `agent` | 仅执行绑定任务中的机器动作 | 不得邀请成员、改变 ACL、批准候选、安装全局插件或自我续权 |

每个源码快照、知识对象、能力版本、预览端点、日志集合和缓存命名空间都记录 `resource_owner`（人或明确的项目小组）、ACL 版本、敏感级别和项目绑定。新增成员继承群默认角色和已明确共享的项目资源ACL，无需逐台配置；不因此得到群范围之外或另有保护的资源；资源主人可以进一步缩小范围，但不能绕过项目策略。Hub 显示两条授权链：谁授予了项目角色、谁批准了资源和版本；缺任一条就返回结构化拒绝，不能以“来自可信成员的文字”补齐。

### 16.3 独立工作区与 PR 审阅

每名研发、每台设备上的代理和每个远程任务使用独立 `workspace_id`、源快照摘要和输出目录；不共享宿主 home、编辑器状态或裸 Git 工作目录。候选至少包含 `base_source_digest`、变更摘要、文件清单、测试/预览证据、提交者身份、代理身份和策略版本。Hub 持久化的是不可变快照和候选引用，不是让多个执行器对同一路径并发写入。

PR 是从独立工作区提交到目标分支的审阅对象。保护分支的更新必须经过项目角色与目标资源主人要求的审阅，必要时由两名不同的人确认；冲突时生成新的候选或要求人工解决，不自动选择一方、不自动覆盖其他工作区、不自动 commit/push/merge。候选基线过期、源摘要或工具链不匹配时，审阅状态回到 `needs_rebase`，旧结果不能覆盖新 attempt。Hub 可以反向分发任务、结果和预览，但不能借此取得研发机的编辑器、Git 凭据或整个桌面。

## 17. 知识共享不是个人记忆同步

团队共享只允许发布到项目命名空间的、可追溯的知识对象，例如已审核的设计决策、脱敏故障结论、运行手册、测试模式和兼容性说明。它不复制个人 `GlobalStore.memory_*`、会话上下文、原始对话、未审核模型推断、访问令牌、环境变量或宿主机记忆；个人记忆仍留在所属会话/设备，除非人主动整理为候选并经过项目审核。知识候选不应改变任何人的系统提示、工具权限或成员角色。

### 17.1 候选、版本、来源与适用源码

每个对象用不可变版本表示，至少包含：

```text
knowledge_id, version, content_digest, project_id, status
source_ref, source_digest, applicable_source_range, toolchain_digest
author_person_id, author_device_id, proposing_agent_id, reviewers
created_at, valid_from, expires_at, supersedes, causation_id
sensitivity, acl_version, policy_version, withdrawal_reason
```

`source_ref` 必须指向项目内可核对的 PR、任务、日志或外部资料引用，`source_digest` 绑定实际来源内容；`applicable_source_range` 说明适用于哪个提交/tree digest、版本范围、工具链或部署 epoch。知识必须记录来源和状态；通用经验可声明不绑定源码，待验证笔记可进入明确标记的项目候选区，但不能冒充已核实结论或自动触发执行。用于自动修改、部署或诊断决策的条目必须有可核实来源、适用条件和版本。相同主题的新版本不覆盖旧版本：Hub 保留版本链、审批者、差异和因果关系，调用方必须选择具体版本或由策略允许的已审核兼容版本。

发布流程为：人或代理创建 `candidate`；策略执行器做秘密/个人信息/跨项目引用检查并冻结内容摘要；资源主人确认来源、适用源码、敏感级别和有效期；由项目授权的审核人确认正确性与兼容性；普通知识不强制独立第二人，高风险可执行规则按项目政策另行审阅；项目协调器将候选提升为 `approved` 并写入审计；索引器只索引已批准版本。代理可以起草和提供证据，不能批准自己的候选。候选、被拒绝和过期版本默认不可被普通搜索命中。

权限检查与对象版本必须在同一授权视图中处理：检索结果携带 `project_id`、`knowledge_id/version`、`acl_version`、`source_digest` 和索引版本；若 ACL epoch、对象版本或项目源码基线在查询期间变化，则重新检查或拒绝，不把旧摘要与新权限拼接。这个要求借鉴 Zanzibar 对集中式权限检查、对象版本和因果一致性的关注，但不搬用其全球规模、拓扑或延迟目标。

### 17.2 检索、缓存与失效撤回

检索先按项目、资源 ACL、敏感级别和成员/设备/代理身份过滤，再排序和生成摘要；不能先建立跨项目向量索引再在末端隐藏结果。缓存键至少包含 `project_id`、资源 ACL/授权 epoch、知识版本、源码基线和模型/摘要策略版本；命中缓存时仍做当前 ACL 检查。嵌入、全文索引、摘要、下载对象和本地磁盘缓存都按项目/信任域隔离，禁止以“内容摘要相同”合并不同项目对象。错误、未命中和拒绝响应也不能泄露另一个项目是否存在该对象。

资源主人或项目管理员撤回时，状态变为 `withdrawn`/`revoked`，递增 ACL epoch，停止新检索和能力引用，通知在线客户端清理对象、摘要、嵌入和预览缓存；离线客户端下次连接必须重新验证，不能凭旧 TTL 继续使用。撤回应记录原因、替代版本、发现范围和清理结果；不能承诺已经被人看到或发送到失陷设备的文本可物理擦除。定期过期、源码不再匹配、工具链漏洞和来源纠正都走同一撤回/重审流程。

现有 `Newbee.GlobalStore.export_bundle/install_bundle`（`lib/newbee/global_store.ex` 的现有导出、兼容性检查和 Change 流程）可作为将审定对象带入项目的底层机制；它当前不等于团队成员 ACL、跨项目检索隔离或知识撤回系统。设计实现必须在其外层增加 `project_id`、资源 ACL、审批和版本/撤回检查，不能把现有 API 描述成已经具备团队授权。

## 18. 单人多机与多人多机的默认连接与端口矩阵

### 18.1 Hub 应用层默认

Hub 是 mTLS 的 TLS 终止点：它能读取经过该连接的项目任务、源码、日志、制品和预览数据；mTLS 提供传输保密、双向身份和连接授权，不等于 Hub 与项目数据之间的端到端内容加密。项目允许 Hub 处理的源码可以经过此通道；长期秘密不进入通用任务消息，由目标端凭据 broker 按用途注入。项目政策禁止 Hub 读取的内容不能走当前内容通道。独立密钥、端点 ACL、生命周期和审计齐备的 E2E 内容通道是后续可选能力，首版不得伪称已经支持，也不得以传输加密替代该数据政策。

Hub 可以部署在专用主机或 `.9` 等受信设备上。若 `.9` 只是第二台研发机，它像 `.8` 一样无入站监听；只有 `.9` 明确承载 Hub 时才开放 Hub 端口。若 Hub 与 Worker 同在 `.20`，`.20` 才需要为 Hub 监听 `443` 或 LAN `8443`，Hub 与 Worker 仍使用不同设备/服务身份和项目 ACL；`.20` 不因运行 Worker 而开放其他入站端口。Hub 位于别处时，`.20` 永远不需要为 Worker 开入站端口。

| 节点/角色 | 主动出站 | 允许入站 | 明确禁止或限制 |
| --- | --- | --- | --- |
| `.8` 研发/UI/Lead | 到 Hub `TCP 443`，或经审批到内网 Hub `TCP 8443`；连接由 `.8` 发起 | 无新增 LAN/公网入站；已建立连接的返回流量由状态防火墙允许 | 应用只绑定 `127.0.0.1`/`::1` 的分配端口；不开放 `3000`、`4000` 或任意 `0.0.0.0/0`；不共享 CDP |
| `.9` 第二研发机（Hub 不在此） | 同上，连接由 `.9` 发起 | 无新增入站 | 与 `.8` 相同；不能因是成员而接受 `.8`、`.20` 的任意 distribution 或工作区写入 |
| `.9` 受信 Hub（仅在明确选定时） | 可主动连接自身外部依赖和已批准的设备；成员仍主动连 Hub | 仅 Hub `TCP 443` 或 LAN `TCP 8443`，来源限于批准的成员/代理网络和 mTLS；不同时无理由开放两者 | 不把 Hub 监听误当成研发应用监听；不开放 `0.0.0.0/0`、`::/0` 或 EPMD |
| `.20` headless Worker（Hub 在别处） | 到 Hub `TCP 443`/LAN `TCP 8443`，由 `.20` 主动发起；可按任务访问批准的 registry/proxy | 无新增入站，Worker 任务和结果均走长连接 | 开发实例只绑定 `.20` 的 `127.0.0.1`/`::1`；不开放 `3000`、`4000`、随机应用端口、SSH 新规则或 CDP |
| `.20` Hub + Worker（特殊部署） | Worker/本机服务主动连接本机 Hub 或外部批准依赖 | 仅 Hub `TCP 443` 或 LAN `TCP 8443`，来源精确限制为 `.8`、`.9` 等已批准端点；Worker 本身仍无入站 | 不把同机 Worker 端口暴露给 LAN；撤销 Hub 不应自动改变现有 SSH 管理规则 |

矩阵中的“到 Hub”是应用层 mTLS，不等同于允许成员互访。正常模式不在成员机开放 `TCP 4369`、`TCP 45101`、3000、4000 或浏览器调试端口；本节没有为 SSH 添加端口，已有 SSH 管理面必须单独保留并由管理员维护。Hub 若置于公网仍只接受证书、项目和资源 ACL 均通过的连接，不以公网 IP、LAN 地址或反向代理的 `X-Forwarded-*` 自称身份。

### 18.2 保留的原生 Erlang 强化私网模式

TLS distribution 只作为显式的私网适配器运行在独立 Bridge VM 之间；每个 Bridge 通过固定、受限的本地 IPC 请求本机策略执行器，策略执行器不加入 distribution 信任集群，也不共享 node cookie/证书。主 newbee VM 和所有团队成员仍不加入一个全互联集群。示例固定分布端口为 `TCP 45101`：OTP `kernel` 的 `inet_dist_listen_min` 与 `inet_dist_listen_max` 都设为 `45101`，并绑定到 Bridge 的明确私网接口；实际 OTP 版本、TLS 节点名和证书行为要先用负向测试确认。

EPMD 默认 `TCP 4369` 只是节点名到 distribution 端口的发现/注册通道，不承载 distribution 数据；它不是因为固定了 `45101` 就自动安全，也不能当成 HTTPS。若所选 OTP 的静态节点配置允许，可以避免跨网 EPMD；若仍使用 EPMD，只允许配对 Bridge 的精确源地址、管理网接口和短时发现窗口，绝不向公网、整个 LAN 或所有项目开放。固定端口和 EPMD 的取舍、节点名校验与证书校验必须在锁定 OTP 版本上验证，不能凭端口号推断安全。

连接方向写入配对记录而不是依靠 `connect_all`：例如 `.8` Bridge 只向 `.20` Bridge 的已批准地址主动拨号，`.20` 只在 `45101` 接受该 `.8` Bridge 的证书/源接口；故障转移到 `.9` 时另建 `.9` 到 `.20` 的明确 pair，不能顺便允许 `.8/.9/.20` 全互联。若 OTP 场景确实要求两端都能主动重连，则每一方向仍只允许命名的对端、固定接口和 `45101`，不能把整个子网加入 allowlist。`hidden` 节点、`connect_all=false` 和限制发现只控制拓扑，不是执行沙箱或项目 ACL；应用任务授权、Bridge VM 隔离和外部策略执行器仍不可省略。

### 18.3 WireGuard、Tailscale 与出站限制

WireGuard 是自托管的点到点/站点隧道：项目管理员持有并轮换公钥、分配地址、选择 UDP 监听端口（常见 `UDP 51820`），并负责 peer allowlist、路由、MTU 和防火墙。它只提供网络加密和对端路径，不替代 Hub 的人/设备/项目/资源授权，也不应因此把所有成员放进同一可信 LAN。

Tailscale 使用其控制面管理身份和 WireGuard 数据路径；UDP `41641`、UDP `3478` 等会影响直连/打洞。若组织已预批准且策略允许，直连受阻时可以继续使用 TCP `443` 的中继路径；该路径仍须满足项目身份、Hub/客户端 ACL 和审计要求。中继 TCP 443 是可用性路径，不等于本地 Hub 的应用 mTLS，也不代表所有端口都需要对公网开放。无论使用哪种 overlay，仍按上面的 Hub ACL、应用证书和项目隔离检查。

若组织出站策略不允许当前选定传输所需的路径，客户端先检查是否存在组织已预批准且策略允许的替代路径，例如已配置的 Tailscale TCP `443` 中继；该路径可用并通过身份、ACL 和 TLS 验证时继续，不因某个 UDP 路径被阻断就单独判定失败。只有当前选定传输没有任何已批准的可用路径时才报告“网络策略阻塞”，并由管理员批准明确的代理、Hub 或防火墙规则后再继续；不得擅自新增 relay、UPnP、NAT 穿透、端口转发、SSH 反向隧道或其他绕过政策的路径。代理做 TLS 检查时必须明确其受信 CA、客户端证书转发/终止边界和端到端 mTLS 语义；无法验证时阻塞，不能关闭证书校验或静默降级。

## 19. 防火墙变更的 plan/apply/verify/rollback

防火墙向导只生成提案，不默认执行。它先以只读方式识别 OS、实际规则管理器和所有可能控制路径：UFW/nftables、firewalld zone、Docker 的 iptables/nftables 链、云安全组、路由器 NAT、IPv4/IPv6 接口和企业代理。计划记录当前规则摘要、监听进程、目标协议/端口、绑定接口、精确来源 CIDR、双栈差异、预计影响、规则拥有者、过期时间、验证命令和回滚 ID。无法确定哪个层实际放行时停止并要求管理员判断，不猜测后端。

`apply` 需要本机或基础设施管理员在显示完整 diff 后明确批准；应用规则必须幂等、带可追踪注释/标签、只增加所需的精确来源与接口，并保留原规则顺序和快照。不得自动 `disable`、`flush`、`reset`、全量 `enable` 或删除既有规则；不得修改 SSH 管理端口、来源限制、云控制面或路由器 NAT，除非它们作为单独项目由管理员批准。任何“临时开放”都要有最短 TTL 和撤销任务。绝不生成 `0.0.0.0/0`、`::/0` 或“任意接口”来解决连接问题。

`verify` 同时检查 `ss`/等价监听结果、实际规则集、IPv4 和 IPv6、Hub 证书/项目 ACL、批准来源的连接与未批准来源的拒绝；还要从真实 NAT/云安全组路径和受 TLS 检查的代理路径各测一次。验证必须确认 Worker 的应用端口只在 loopback，Hub 反向任务/结果/预览可用而不出现任意 TCP 转发。Docker 发布端口可能由 Docker 的 iptables/nftables 链绕过 UFW 表象；若使用 Docker，计划必须检查 Docker 规则、`DOCKER-USER`/等价策略、发布绑定和容器网络，不能仅以 `ufw status` 通过。

`rollback` 只删除该计划创建的带 ID 规则或恢复经用户批准的精确快照，并再次验证 SSH、Hub 和 IPv4/IPv6 状态；不能用“清空后重建”回滚。若 apply 后验证失败，默认撤销本次新增规则并保留管理面，报告云安全组/NAT/代理等外层差异；远程离线时不宣称已经回滚。

以下只是一段**文档中的受限 UFW 示例，不执行，也不是可直接复制到任意主机的命令**。假设 Hub 在 `.20`、选择 LAN `8443`，并且 `.8`、`.9` 的地址已由管理员确认；实际实现应先生成 plan、查看当前规则并由管理员批准。若选公网 `443`，应生成等价的精确来源规则，而不是把来源改成全网。

```text
# review-only illustration; choose 443 OR LAN 8443, never both by default
sudo ufw status numbered
sudo ufw allow in on <hub-lan-if> from 192.168.0.8 to any port 8443 proto tcp comment 'newbee-hub .8'
sudo ufw allow in on <hub-lan-if> from 192.168.0.9 to any port 8443 proto tcp comment 'newbee-hub .9'
sudo ufw status verbose
# IPv6 clients require separately reviewed exact /128 or approved IPv6 CIDR rules.
# Rollback removes the recorded rule IDs only; it never flushes UFW or touches SSH.
```

IPv6 的监听、路由和规则必须单独显示；IPv4 allowlist 不自动覆盖 IPv6。云安全组/NAT 的端口转发不必然绕过正确的主机防火墙，但 SNAT/转发可能改变主机看到的源地址，Docker 也可能把流量带入不同的 iptables/nftables 链和容器路径；计划必须从真实客户端经云、NAT、主机和容器的端到端路径核对实际规则命中和拒绝结果，不能只凭某一层推断暴露或安全。默认不创建端口转发；代理 TLS 检查若替换 Hub 证书，必须明确终止点和受信 CA，否则 mTLS 验证失败即拒绝连接。应用开发端口和预览服务永远只绑定 loopback，不通过开放 `3000`、`4000`、`0.0.0.0`、`[::]` 或共享 CDP 来规避 Hub 设计。

## 20. 能力共享：远程调用与安装 recipe/plugin

能力共享分成两个不可互换的平面：

1. **远程调用**只调用 Hub/Worker 已注册的窄 API。它不把源码、函数名或任意 Erlang term 变成远程 shell，也不改变调用方的项目角色。
2. **安装 recipe/plugin**把可执行代码或工具链候选放进隔离的项目工作区/Runner。安装、激活和回滚分别审核；能力广告、registry 命中或兼容性通过都不等于批准安装。

能力注册摘要至少包含：

```text
capability_id, kind, version, content_digest, summary, api_schema_digest
project_id, compatible_source_range, toolchain_digest, dependencies
required_actions, data_read_scope, data_write_scope, network_egress
sandbox_profile, cpu_memory_pid_disk_time_quota, concurrency_limit
secret_policy, resource_owner, reviewers, status, expires_at
rollback_ref, provenance, policy_version, approval_event, withdrawal_reason
```

`version` 和 `content_digest` 必须被任务锁定，不能解析为“最新”；摘要、来源、适用源码版本、权限、沙箱、配额和回滚引用都在审批页面展示。能力输出也标记数据敏感级别和来源，不能因为输出来自受信 Worker 就跨项目写入知识索引或缓存。

### 20.1 远程调用生命周期

调用方先以成员、设备和代理身份请求已批准的 `capability_id/version` 与具体操作；Hub 检查项目角色、资源主人 ACL、调用方源码范围、版本摘要、过期时间和剩余配额；Worker 再用本地策略重复检查。请求只接受固定 schema、对象引用和有限枚举，不接受任意 `module/function/args`、任意 URL、任意宿主路径或任意网络转发。执行在 non-root/无特权沙箱内完成，限制 CPU、内存、PID、磁盘、时长、并发、输出大小和出站域名；调用、拒绝、取消、配额耗尽和结果摘要都审计。

远程调用可以由代理提出，但高风险动作仍需资源主人/第二审批者的人签名；调用票据不允许再签发票据、邀请成员、改 ACL、写保护分支或安装其他能力。撤销时 Hub 停止发新调用，Worker 拒绝续租并清理任务；已经返回的数据按已外发数据处理，不能承诺收回。

### 20.2 recipe/plugin 安装生命周期

recipe/plugin 先进入项目隔离 staging，做签名/来源、内容摘要、依赖锁定、静态 contract、兼容源码/工具链、秘密扫描和沙箱能力检查；然后由项目角色审阅，资源主人确认读写范围、网络和配额，项目协调器通过 Change 记录候选批准。已有 `GlobalStore.install_bundle` 的兼容性检查和 Change 提交流程可复用，但团队 ACL、候选审核、项目作用域、版本撤回和回滚必须由外层策略提供，不能假设现有 API 已实现这些控制。

安装成功不等于激活：默认不自动 hotload、`Code.ensure_loaded`、替换正在运行的模块或重启别人的会话。激活必须是明确、可审计的动作，优先启动新的隔离 Runner/版本化任务；需要重启时显示影响范围和旧版本 `rollback_ref`。回滚恢复上一个已批准的摘要、撤销新版本的调用票据、清理其工作区/缓存和可停止副作用；不可逆副作用未能 fencing 时进入 reconciliation，不自动宣称成功。跨项目安装、全局插件或写宿主服务都默认拒绝。

### 20.3 能力共享操作场景

1. `.8` 的开发者请求 `.20` 的受限诊断能力。Hub 显示版本摘要、源码基线、只读文件范围、网络为无、每次/每日配额和结果敏感级别；项目角色与资源主人批准后，Worker 在隔离 Runner 执行并回传引用。诊断代理不能顺便取得 shell、源码全量或部署权限。
2. 团队需要一套构建 recipe。开发者提交带来源、lockfile、工具链摘要和适用提交范围的候选；审核者检查安装脚本和出站域名，Owner 批准项目范围，`GlobalStore` 兼容性/Change 通过后只装入 `.20` 的 staging。首个任务显式激活新 Runner，旧工作区不被覆盖；失败按 `rollback_ref` 恢复。
3. 某 plugin 被发现依赖漏洞。资源主人撤回该版本并递增授权 epoch；Hub 拒绝新远程调用和安装，Worker 排空或终止可控任务，缓存/索引清理，项目管理员审阅已批准的旧版本或修复版本。在线设备看到撤回审计，离线设备下次连接不能凭本地缓存继续调用。
4. 两名研发各自修改同一 recipe。各自提交独立 workspace/PR，Hub 保存两个源摘要和测试证据；Reviewer 只批准与目标资源主人授权一致的候选。冲突、过期基线和不同依赖锁不会自动覆盖、合并或选择“较新”版本。

## 21. 新增验收用例

以下是实现前应加入的结构化验收；均只在可丢弃测试环境执行，不在本设计阶段修改主机或防火墙。

| 用例 | 必须观察到的结果 |
| --- | --- |
| 人邀请、设备登记、代理签发 | 过期/重放邀请、错误设备证书和未绑定代理均拒绝；代理令牌包含人、设备、项目、任务、范围和期限 |
| 成员主动退出/管理员撤销 | epoch 递增，长连接/任务/预览/续租和新检索立即拒绝；离线状态明确显示待确认，不伪造远端清理 |
| 角色与资源主人双重授权 | 只有角色、只有资源 ACL、代理自批或跨项目重放任一情况均拒绝；角色与资源 ACL 均通过；需人工确认的范围变更已确认，仅项目政策指定的高风险动作要求独立第二人 |
| 独立工作区与 PR | 两个 workspace 同时改同一文件不会互相覆盖；过期基线进入 `needs_rebase`；没有自动 commit/push/merge |
| 知识候选与版本 | 缺来源、源码范围、审核或摘要不进入普通检索；检索返回对象版本、来源、ACL epoch 和适用基线，不能返回另一项目结果 |
| 知识缓存 ACL | 相同正文在两个项目中使用不同 ACL 时缓存键不合并；撤回后旧索引、嵌入、摘要和离线缓存不能通过当前检索返回 |
| 知识撤回与因果一致性 | 撤回与新版本并发时旧版本不复活；ACL/对象/索引版本不一致则重查或拒绝，不混合新权限和旧内容 |
| 远程能力调用 | 未批准 API、任意模块/URL、跨项目对象、超配额、过期版本和代理提权均拒绝；固定 schema、配额和审计有效 |
| recipe/plugin 安装 | 摘要/来源校验/兼容性/Change/对应风险等级授权缺任一项不安装；安装不自动 hotload；显式激活可追踪且可回滚 |
| 能力撤回/回滚 | 撤回阻断新调用，清理可达缓存并停止可控任务；旧版本恢复后摘要、权限和审计与批准记录一致 |
| Hub 默认连接 | `.8`、`.9`、`.20` 只能主动 mTLS 连接批准 Hub；Hub 只选 `443` 或 LAN `8443`；Worker 无新增入站；任务/结果/预览能反向送达 |
| Hub 在 `.20` 的特殊部署 | 只有 Hub listener 在 `.20` 开 `443`/`8443`，Worker/应用仍无入站；`.8`/`.9` 精确来源和 mTLS 之外的扫描被拒绝 |
| 应用端口与 CDP | `.20` 开发实例只监听 loopback；LAN 扫描看不到 `3000`、`4000`、随机应用端口和裸 CDP；受控预览仍可用 |
| Erlang 私网适配器 | `45101` 固定、`4369` 仅按已批准发现使用；错误证书/节点名/源接口/非配对方向拒绝；`.8/.9/.20` 不形成全互联，Bridge 失陷仍不能越过策略边界 |
| WireGuard/Tailscale/NAT | 分别验证直连、当前已批准的 TCP 443 中继和实际 NAT 路径；某个 `41641`/`3478`/`51820` UDP 路径被阻断不单独判失败，已预批准且可验证的 relay 可继续；只有没有任何已批准可用路径时才进入 blocked，不自动打洞、UPnP、relay 或反向隧道 |
| 防火墙 plan/apply/verify/rollback | plan 是只读且显示后端、IPv4/IPv6、来源、SSH 影响、Docker/云/NAT 路径；未批准不 apply；apply 不 disable/flush/enable；verify 测通过/拒绝；rollback 只撤销带 ID 规则 |
| Docker、云安全组与代理 | Docker 发布端口不能绕过项目策略；云 SG/NAT 未批准不改变；TLS 检查替换证书或无法保持 mTLS 时拒绝，不静默关闭校验 |

## 23. 第一性原理与全研发链路审视

本节是对前述设计的产品审视和实施取舍；安全细节描述可选能力的约束，不意味着全部进入首版。目标是让研发把正确版本的代码交给合适机器执行，及时拿到可核对的结果，并在失败时知道如何继续。机器数量、代理数量和协议种类本身不是用户价值。

### 23.1 两个一等场景，共用一个执行底座

| 场景 | 用户要完成的事 | 默认交互与约束 |
| --- | --- | --- |
| 单人多机 | 在有界面的机器研发，利用多台无界面/不同架构/不同算力机器构建、测试、运行应用；汇总结果再决定下一步 | 一个人管理多个设备和项目；不要求第二成员。可指定机器，也可在已授权机器中按工具链/架构/资源/数据驻留/可用性匹配。设备仍有独立身份，不因同一个人拥有就自动共享所有数据和密钥 |
| 多人多机协作 | 多研发共同开发项目，借用获准的机器能力，并行处理任务，审阅和交接成果 | 在相同接入、任务和结果协议上增加成员权限、资源主人授权、公平排队、独立工作区与审阅；一人可以有多台机器，一台机器也可服务多个获准成员 |

默认所有设备主动连接同一个项目 Hub；Hub 可与某台 Worker 同机，不强制增加第三台服务器。界面区分“我的设备”和“项目可用资源”，不要求用户选择传输协议。默认不在每个节点启动一个独立决策 AI：构建、测试和运行由确定性 Runner 执行，AI 仅在分析/修改/协商确有价值时参与。

多机不能靠广播任务实现。每个任务明确接收设备、执行身份、输入版本、配额和结果归属；只在授权集合内调度。首版支持指定机器、能力匹配和有限并发，不宣称自动选择最快/最便宜机器。共享机器设置每成员和项目配额，显示排队原因，保留取消和管理员排空维护能力。

可并行的跨架构构建/独立测试共享同一源码快照，各自回传带平台和工具链的结果；汇总页区分失败、未执行和不适用，不把任意一台成功当作全部成功。存在依赖的阶段按既有任务依赖顺序执行；不把任意编译命令自动拆成分布式编译。失联改派先查询原执行状态，涉及部署/迁移等副作用时不盲目重跑。

### 23.2 全研发链路的必要行为

| 阶段 | 必须形成的闭环 | 边界及失败出口 |
| --- | --- | --- |
| 需求与任务准备 | 引用现有 issue/需求，记录目标、验收条件、源码基线和允许的数据范围；用户可直接发起临时任务 | 不强制迁移到新的需求管理平台；含糊的验收必须澄清，不能用“代理说完成”代替 |
| 接入与环境准备 | 一次向导检测设备、隔离、工具链、依赖代理、网络和权限；复用项目已有脚本/容器配置/lockfile | 显示缺失项和下一动作；项目配置仍是不可信输入，安装依赖也是沙箱内执行代码，不自动执行特权 bootstrap |
| 编码与同步 | 支持未提交修改；按批准清单同步差异，以不可变快照绑定每次任务。可检查实际发送文件及大小 | 不要求每轮 commit/push；忽略规则与秘密扫描不能代替发送授权；不可传的链接/子模块/LFS 内容给出明确限制或显式物化方案 |
| 多机构建与测试 | 根据平台和任务类型分配，复用受隔离缓存，记录源码/工具链/依赖与制品摘要；支持有依赖的有限并行 | 冷启动下载、排队与实际执行分开显示；架构/ABI 不匹配在部署前拒绝，缓存不能跨越成员或项目授权 |
| 运行与持续调试 | 同一开发会话保持实例和预览入口，支持增量构建、HMR、日志与失败后再次运行；多个候选不争抢同一端口 | 每次更新有递增源码版本，验收绑定实际已服务的版本；“文件已同步”不等于“应用已就绪”，旧浏览器结果不得验收新版本 |
| API、数据库与依赖服务 | 一个开发环境描述可包含应用、测试数据库和明确的依赖端点；种子/迁移/重置有可见状态 | 每成员/工作区隔离数据和命名空间；运行时短期凭据由目标端 broker 注入，不经过编译器或通用日志；默认不用生产数据。破坏性重置确认，数据库恢复不能冒充制品回滚 |
| 浏览器与集成验收 | .8 可操作远端应用；覆盖 HTTP/WebSocket/SSE、HMR、HTTPS、安全 cookie、登录回调和测试服务 | 稳定入口按项目/环境/访问者隔离；第三方 OAuth 回调地址与测试账号须事先配置。外部 webhook 必须有获批入口；没有时说明该测试不支持，不暗开公共隧道 |
| 多人并行与交接 | 任务交接包含基线、变更、制品、失败证据和剩余问题；结果进入既有 PR/审阅流程 | 独立工作区不互相覆盖；合并冲突返回原开发者处理；共享开发环境显式预约/串行晋级，不以“最后完成者覆盖”代替治理 |
| CI、发布与运维反馈 | 导出可复现构建说明和制品引用，关联现有 CI 状态、审阅与发布记录；线上反馈可回到原任务 | 研发通过不等于生产可发布；发布只能晋级 CI 接受的制品，按既有门禁授权。首版不接管生产部署/迁移/值班平台 |
| 知识沉淀与退出清理 | 从任务证据生成项目候选，确认后共享；到期资源、临时数据、预览和访问授权可查可清理 | 普通笔记和可执行能力分别治理；共享知识不自动变成系统指令。保留必要结果再清理工作区，不以结束任务为由删除用户未导出的修改 |

非浏览器应用仍能通过日志、测试报告、制品和受限 API 检查完成验收；浏览器不是所有项目的强制依赖。调试器断点、任意端口映射、公共预览和外部 webhook 接入是单独能力，只有明确支持的适配器和授权范围可用。

| 审视结论与原位置 | 修订决定 | 可验证的完成条件 |

### 23.4 不可推迟的底线与易用性验收

身份与资源授权、传输保护、实际执行隔离、秘密最小暴露、按接收者投递、持久回执与去重、配额、取消、撤销和受控预览是基础能力。安全实现应承担复杂度：证书按已有信任受限续期、授权范围内自动执行、错误给出定位与修复动作；不得让用户用关闭防火墙、共享 root 密钥或放开任意端口换取可用性。策略变更/证书失陷仍需重新确认，不能以易用性自动扩大信任。

UI 立即显示本地已收到请求，与远端持久 accepted 分开；连接心跳与应用进度分开。沉默达到配置阈值时显示最后事件、正在等待的系统和诊断入口，不自动判死或重发副作用。停止请求显示 requested/已确认/待远端确认；结果未知进入核对流程。关闭 .8 界面后，已批准的任务按既定预算运行，重开恢复相同任务，而不是启动一份副本。

初始验证采用两组真实路径：单人使用至少三台机器完成一次跨平台任务及浏览器修复循环；两名研发使用各自设备和共享 Worker 同时修改同一项目，经历排队、交接、撤销与断网重连。记录首次成功所需人工步骤、正常修改到可用预览的冷/热耗时、重复审批次数、失败定位/恢复耗时和遗留资源数。与同一环境下人工 SSH/现有 CI 流程比较；按实测再定延迟与容量目标，目前没有跨主机性能数据。

验收失败条件包括：正常迭代被重复确认打断、无法指出当前源码/主机/阶段、重试产生重复副作用、权限变化后继续命中未授权缓存、实例清理误删修改、成员退出后仍能新建任务。只有最小流程已被真实使用证明缺能力，才扩充协议和平台模块。

## 24. 项目协作群：交互与使用定稿

状态：用户已认可本版交互，尚未实现。第7节接入和第16节默认权限已同步调整。本节定义普通使用路径；前述底层权限、资源与协议约束由系统实现，不要求用户先理解或逐项配置。

### 24.1 产品入口：建群 → 加入 → 发任务 → 看结果

一个群默认对应一个项目。建群使用当前打开的项目，明确展示共享项目及默认排除项；不会自动共享本机其他项目、个人会话或系统凭据。一个人或设备可以加入多个项目群，各群任务、工作区、缓存及凭据隔离。正确口令加入者可访问这个群明确共享的项目内容，创建者必须能在建群时理解这一点；另有保护的内容不因入群解除限制。

```text
创建项目协作群

群名称    [订单系统开发组             ]
项目      当前项目：order-system
加群口令  [自动生成，可修改           ] [显示]

当前项目的协作代码、群任务和结果将与群成员共享。
默认排除凭据及私人数据，可查看实际发送文件。
                         [创建协作群]
```

口令至少8位，默认生成16位随机口令，拒绝常见弱口令。建群后显示群名称、可达地址和口令，提供“复制邀请”“显示二维码”。邀请包含群身份校验信息；界面不要求填写端口、证书或协议，非默认端口自动包含在群地址中。手动输入裸IP仍须按第7节验证服务器身份，不能因简化表单关闭认证。

### 24.2 加入：不增加资源配置页面

```text
加入协作群

群地址    [192.168.0.20               ]
群口令    [****************           ]
显示名称  [Alan 的开发机              ]

加入后，本机可参与该项目的任务执行。
任务使用专用隔离工作区，不自动开放私人目录和系统凭据。
                         [加入协作群]
```

正确口令默认直接加入，不紧接着弹出群主审批或目录/命令/端口/CPU配置向导。系统自动完成身份登记、工具链与隔离能力检测、工作区准备、默认配额和受限设备凭据续期，显示实际进展。准备完成后进入群；缺少工具或隔离后端时显示具体问题、修复入口及当前不能接收的任务类型。不能把“已加入”显示成“所有任务都能执行”。

无GUI设备提供等价终端流程与状态输出；口令隐藏输入，终端不依赖浏览器或裸CDP。日常在有界面的设备管理群。群口令用于接入，之后每台设备使用独立凭据；改口令阻止旧口令继续加入，已登记成员/设备通过单独撤销退出，二者在设置中区分。移除成员可一并撤销其设备，移除单台设备不误踢该成员其他设备。


首页优先回答谁在做什么、在哪台机器执行、是否阻塞、有什么可用结果。无已验证账户关联时显示成员/设备条目，不凭昵称假定归属于同一个人。机器架构、工具链、配额、指纹和连接诊断在详情中展示。尚未实现的知识检索等可选能力不显示成可点击的已完成产品功能。

### 24.4 发任务：默认自动安排，必要时调整

用户可直接输入：“在合适的机器上编译项目，运行测试，启动开发环境，我在本机浏览器验收。”任务卡解释系统的安排：

```text
构建并启动开发环境
项目版本：当前修改，包含未提交文件
执行安排：编译机20 构建、测试并运行应用
完成之后：本机提供浏览器入口
[开始]                                  [调整安排]
```

用户提出探索性计划时先展示安排；明确要求立即执行且已在默认范围内时，直接展示运行卡，不再要求点一次“开始”或重复确认资源授权。输入不明确、超出范围或有重大副作用才停下询问。调整安排支持指定机器、指定参与者、多机分别测试和本次资源上限；系统不为显示协作而强行拆分简单任务。

调度只使用同群、获准且满足工具链/平台/隔离/数据范围的设备；多机结果分别记录并汇总失败、未执行和不适用。任务卡展示当前源码版本、执行阶段、机器和下一步，不把排队当执行。未提交修改可随明确文件清单发送，不要求每轮commit/push。

### 24.5 持续开发：环境卡稳定，验收版本固定

```text
订单系统 · Alan 的开发环境
运行机器：编译机20
状态：已就绪
当前版本：14:32 的修改
[打开应用] [查看日志] [重启] [停止]
```

环境围绕开发会话持续存在，而非每发一个任务就换浏览器入口。修改后依次显示同步中、更新/构建中、应用就绪，并记录实际提供服务的源码版本；支持的框架使用HMR，否则明确重建。正常会话在已批准预算内保持入口、登录状态和开发数据，过期与空闲回收提前可见。

稳定入口不削弱隔离：每个人/工作区默认独立环境、浏览器身份和测试数据，不复用管理UI的cookie或凭据。OAuth回调、HTTPS和测试服务按项目适配；没有批准的外部webhook入口就说明限制。测试报告与浏览器验收绑定具体就绪版本，不能把旧页面的结果验收新代码。

确需共用环境时，在环境卡明确标记“共享”，更新排队并使用目标端防重/栅栏；不让最后完成的旧任务覆盖新版本。非浏览器项目仍可通过日志、制品、测试报告和受限API检查验收。

### 24.6 两个场景与成果交接

| 场景 | 日常用法 |
| --- | --- |
| 单人多机 | 创建项目群，加入自己的开发机、编译机和测试机；系统选择合适设备，用户在当前机器发任务、查看汇总和操作应用 |
| 多人多机协作 | 同事带自己的设备加入同一项目群；任务可交给某人、某台机器或自动安排，成果回到群内，设备共享执行但工作区和数据保持隔离 |

“交给小李”附带源码基线、当前进展、代码变更、失败日志、验收条件及剩余问题。接收者不必翻完整会话重新猜上下文。任务交接不能隐含转移生产凭据或管理员身份。

```text
小李提交了订单接口修改
[查看变更] [运行验证] [接受到我的工作区] [反馈问题]
```

“接受”先校验基线和本地修改，不静默覆盖；冲突明确呈现并由用户处理。正式审阅和合并复用已有Git/PR流程，接受到工作区不等于自动commit/push/merge。

### 24.7 本机控制：一个常用开关

```text
本机参与协作：开启
[暂停接收新任务]
```

暂停仅停止接新任务，已运行任务继续显示并可单独停止。资源占用、并发、保留时间和工具链使用默认配置，在高级设置调整；同一设备参加多个群时，总资源限制也必须生效，不能各群分别占满机器。退出群停止新接单、撤销连接与访问，并显示运行任务和数据清理的实际结果。

额外确认只在实际需要时出现：读取群项目外的本机内容；使用新增凭据或修改系统配置；公开应用、访问生产或进行破坏性操作。既有范围内的构建、测试与私有预览不重复打断。可信群成员提交的代码仍在沙箱中执行，口令不等于宿主机通行证。

### 24.8 故障交互与首版验收

```text
完整测试                           等待依赖下载
执行机器：编译机20
最后活动：12秒前
当前情况：依赖服务器连接失败，正在有限重试
[查看详情] [停止]
```

界面区分排队、运行、等待输入、网络失联、失败和结果未知。失联提示“任务是否完成尚未确认，恢复后核对结果”，不一直转圈，不伪报完成。重试显示是否安全：构建确认原状态后可重新安排，部署/数据库操作必须先核对副作用。重开客户端恢复同一个任务，不自动创建副本。

| 验收路径 | 必须观察到的行为 |
| --- | --- |
| 单人三台机器 | 无需第二成员或逐项资源配置；能识别不同能力、安排独立任务并汇总结果；GUI机器操作无GUI机器上的应用 |
| 多人共享多台机器 | 正确口令直接加入；项目默认范围可用，其他项目不可见；任务排队、交接和本地冲突处理明确 |
| 日常迭代 | 明确执行指令直接运行；稳定预览连续更新，登录/数据在授权会话内保留；验收不串源码版本 |
| 暂停与占用 | 暂停不杀已有任务，停止可确认；多群合计资源不超本机限额 |
