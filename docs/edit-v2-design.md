# Edit v2：面向大模型的版本化文件编辑事务

> 状态：**已实现**（2026-08，PR #12 stage B + PR #17 clean_hash）。
> 落位：`lib/newbee/tools/edit/v2.ex`（补丁层）+ `lib/newbee/tools/edit/snapshot_store.ex`（快照仓库）+
> `lib/newbee/tools/edit.ex`（show 集成 v2 快照标签）。行号全部指向原快照；
> stale/越界/未读/重叠/no-op 一律拒绝，多节预检全过后原子落盘（逻辑原子）。
> 协议见模块 `@moduledoc`：`[path#tag]` + `PUT N..M / PUT <N / PUT >N / CUT N..M`。
>
> 目标：重新设计 `Newbee.Tools.Edit` 的模型接口和落盘协议。本文讨论的是“模型已经形成修改意图之后，如何可靠地把意图变成文件状态变化”，不讨论模型如何理解需求或生成正确算法。

## 1. 问题定义

大模型不是确定性编译器。它可能：

- 抄错行号、哈希、缩进或旧文本；
- 混用补丁语法；
- 忘记文件在读取后已经变化；
- 在一次回复中修改多个相距很远的区域；
- 正确理解需求，却在机械落地阶段失败；
- 生成语法正确、但语义错误的代码。

文件系统也不是静态输入。用户、格式化器、另一个 agent 或热重载进程都可能在模型读取后修改文件。

因此 Edit 工具不是一个普通的 `String.replace` 包装器。它处在两个不可靠边界之间：

1. 上游是概率性的模型输出；
2. 下游是随时可能变化的文件状态。

它的本质应定义为：

> **把模型声明的局部修改意图，转换成经过版本校验、冲突检测和原子预检的文件事务。**

工具不应猜模型“可能想改什么”，也不应替模型决定业务语义。它负责的是准确寻址、安全提交、明确失败和低成本重试。

## 2. 代价排序

从工程风险看，三类结果的代价不对称：

1. **静默错改**：最高代价。可能覆盖用户修改，且模型继续基于错误状态工作。
2. **安全拒绝**：中等代价。浪费一次工具调用，但文件保持正确。
3. **要求重新读取**：最低代价。增加少量输入 token 和一次调用。

所以核心排序是：

```text
不静默错改 > 尽量一次成功 > 节省 token
```

任何“提高成功率”的宽松机制，只要可能把不确定目标自动落盘，就不应进入提交路径。模糊匹配可以用于诊断和建议，不能用于自动写入。

## 3. 工具要帮助模型的方面

### 3.1 降低协议认知负担

模型真正需要表达的是：

- 哪个已读取版本；
- 原版本的哪一段；
- 这段最终应变成什么。

逐行哈希、相邻上下文哈希、重复行消歧和重定位算法都是工具内部问题，不应让模型手工组装。

收益：

- 更少专有语法；
- 更少机械抄写错误；
- 更短的系统提示和错误说明；
- 不同模型更容易稳定遵循同一协议。

### 3.2 建立明确的状态边界

模型必须能指出“我是依据哪个文件版本编辑的”。工具必须在提交前验证该版本，不能只验证碰巧未变化的一两个边界行。

收益：

- 检测用户或其他进程的并发修改；
- 防止长范围替换覆盖中间发生的变化；
- 支持可证明的安全重定位，而不是猜测。

### 3.3 减少输出 token

模型只输出变化后的内容，不重抄未变化的旧块，也不为每行复制哈希。

收益：

- 降低生成延迟和费用；
- 减少长内容中缩进、引号和空白复制错误；
- 避免失败后的重复输出和重试循环。

### 3.4 提高失败的可恢复性

工具错误必须告诉模型下一步该做什么，而不是暴露解析器内部规则。

例如：

```text
文件版本已变化，未写入。
原目标 626..635 中第 631 行已被修改，不能安全重定位。
请使用下面的新快照和 625..637 行重新生成补丁：...
```

收益：

- 模型不需要理解内部实现；
- 一次错误通常只需一次确定性的修复；
- 减少同一错误反复尝试。

### 3.5 保持语言无关

核心寻址以文件版本和文本行范围为基础，对 C、Python、Elixir、JavaScript、CSS、Markdown 都适用。

语法树只能作为可选便利层：把“函数块”解析成具体范围后，仍进入同一个版本化事务。解析器不可用时，核心编辑能力不应失效。

### 3.6 提供可验证反馈

成功结果必须包含：

- 实际修改的文件；
- 紧凑 diff；
- 新文件版本标签；
- 修改后的局部行号和内容；
- 是否发生了安全重定位；
- 可选的格式化、语法检查或测试结果。

这样模型下一步可以直接建立在已提交的新状态上，不必猜测落盘结果。

## 4. 核心设计

### 4.1 模型看到的读取结果

读取或 `Edit.show/2` 返回文件快照标签和普通行号：

```text
[priv/web/style.css#c91478a62f3b]
625| /* Mission Control */
626| .mc-expand {
627|   position: fixed;
...
635| .mc-expand:hover { background: var(--accent); }
636|
637| #mission-control {
```

标签是当前会话快照的短句柄。工具内部保存：

- 完整规范化文本；
- 完整内容摘要；
- 原始换行格式、BOM 和尾换行状态；
- 模型实际看过的行范围；
- 路径和记录时间。

短标签只是模型复制的句柄，不是唯一安全依据。查到快照后仍要比较完整摘要或完整文本；短标签碰撞不能造成错改。

### 4.2 模型提交的最小补丁语言

只保留三个基本动作：替换、插入、删除。

```text
[priv/web/style.css#c91478a62f3b]
PUT 626..635:
+.mc-expand.hidden { display: none; }
```

同一文件多处修改放在同一节中；所有行号都指向该节标签对应的原始快照：

```text
[priv/web/index.html#71c28f5d30aa]
PUT <40:
+      <button id="mc-expand" class="icon-btn">...</button>
CUT 82..82
```

规范语法：

```text
PUT N..M:   用后续最终内容替换原快照的 N 到 M 行
PUT <N:     在原快照第 N 行之前插入最终内容
PUT >N:     在原快照第 N 行之后插入最终内容
CUT N..M    删除原快照的 N 到 M 行
```

正文每行使用 `+` 前缀，仅用于区分协议和内容；正文表示最终内容，不混入旧内容或 diff 上下文。

设计约束：

- 文件标签必填，不做成可选；
- 模型不再复制逐行哈希；
- 不要求模型提供相邻上下文哈希；
- 不允许补丁中的行号受前一项操作影响；
- 同一文件的范围不得重叠；
- 新文件和整文件重写继续使用 `Fs.write`，不挤进局部编辑协议；
- 跨文件移动、寄存器和语法块是后续扩展，不进入首版核心。

### 4.3 为什么不把精确内容替换作为统一默认

精确内容替换很容易理解，但模型必须完整重抄旧文本。它有三个固有问题：

- 输出 token 随旧块大小增长；
- 空白、缩进和引号复制失误会导致找不到；
- 同样内容出现多次时必须再增加上下文。

因此首选协议是“快照标签 + 原始行范围 + 最终新内容”。

但不同模型对协议的遵循能力不同。系统可以保留独立的精确内容替换模式：

```text
path + snapshot + exact_old + final_new
```

它必须满足：旧内容精确唯一命中、快照关系可验证。精确匹配失败时可以返回候选差异，但不能自动用模糊候选落盘。

选择哪种模型接口应由同模型、同任务的基准结果决定，并在一个会话中保持稳定；不能按“修改超过五行”之类未经验证的阈值临时切换语法。

## 5. 提交算法

### 5.1 正常路径

一次调用分成五个阶段：

1. **解析**：解析全部文件节和操作，不写文件。
2. **预检**：加载标签对应快照，验证行号、已读范围、重叠、正文和 no-op。
3. **并发校验**：读取当前文件，比较完整版本。
4. **生成候选**：所有操作基于原快照坐标计算，形成每个文件的完整候选内容和 diff。
5. **提交**：再次做比较并交换，成功后记录新快照，返回 diff 和新局部上下文。

任一文件预检失败时，所有文件都不进入提交阶段。

### 5.2 文件没有变化

如果当前内容与快照一致，直接按原始行范围应用。模型无需提供逐行哈希，因为文件级版本已经证明坐标仍对应同一内容。

### 5.3 文件发生变化

默认不是立即猜测，也不是只发一个笼统的 stale 错误。工具尝试“可证明的安全重定位”：

1. 比较旧快照和当前文本；
2. 对替换或删除，要求目标范围内的每一行都保持不变，并映射到当前文件中唯一、连续的区域；
3. 对插入，要求插入点两侧边界保持不变并仍然相邻；文件头尾使用对应的单边规则；
4. 要求所有映射唯一且互不重叠；
5. 任一目标行被修改、删除、复制成歧义区域或移动不明确时，拒绝落盘；
6. 只有全部条件可证明时，才在当前文本上应用，并明确返回“已安全重定位”的警告。

这相当于局部的乐观并发控制。它允许文件其他位置发生无关修改，同时保护模型准备覆盖的全部旧内容。

当前 v1 只检查范围端点和少量上下文时，范围中间的并发变化可能被覆盖；v2 必须验证整个被替换范围。

### 5.4 已读范围约束

模型只能修改它在该快照下实际看过的行。部分读取时，快照保存已展示行集合。

- 替换和删除要求整个原范围已展示；
- 插入要求相邻边界已展示；
- 操作落入折叠或省略区域时拒绝，并返回需要读取的最小范围。

这不是为了限制模型，而是防止它根据过期记忆或结构摘要编辑未见正文。

### 5.5 落盘原子性

“解析全部成功后再写”只叫原子预检，不等于崩溃级多文件原子提交。实现中要区分：

- **逻辑原子性**：任何解析、版本或冲突错误发生时零文件改变；
- **进程内提交安全**：按固定顺序锁路径，临时文件写入后再替换，写失败时用备份回滚；
- **崩溃恢复**：多文件事务写小型 journal，进程重启后完成或回滚未完成提交。

首版至少实现逻辑原子性和进程内回滚，文档不得把它夸大为文件系统提供的全局原子事务。

## 6. 明确不做的事

### 6.1 不自动模糊落盘

忽略缩进、编辑距离、相似块或语义向量都可用于生成诊断候选，但候选不能自动写入。Python 缩进和 C 宏等场景中，“看起来相似”不等于等价。

### 6.2 不把语义正确性混入寻址层

Edit 可以调用格式化器、解析器、LSP 或测试作为提交后验证，但这些是独立的后置条件。版本和范围正确，不代表业务代码正确；反之，解析器暂时不可用也不应阻止纯文本文件编辑。

### 6.3 不同时向同一模型灌输多套默认语法

工具可以有多个后端，但一个模型会话只暴露一套稳定契约。多套相似语法会增加格式串扰和重试。

### 6.4 不因当前一次失败就放宽安全条件

连续失败应返回更好的上下文或切换经配置的模型模式，不能在同一次调用中从精确校验悄悄降级为猜测。

## 7. 结果与错误协议

成功结果建议包含结构化字段：

```elixir
%{
  status: :applied,
  files: [
    %{
      path: "priv/web/style.css",
      old_tag: "c91478a62f3b",
      new_tag: "6bc21dd2ac91",
      relocated: false,
      changed_lines: {626, 626},
      diff: "...",
      context: "624| ...\n625| ...\n626| ..."
    }
  ],
  warnings: []
}
```

错误使用稳定类别，而不是让模型匹配自然语言：

```text
:parse_error
:unknown_snapshot
:stale_conflict
:unseen_range
:ambiguous_mapping
:overlap
:out_of_bounds
:no_op
:commit_failed
```

每个错误同时返回：

- 哪个文件、哪个操作失败；
- 是否写入了任何文件；
- 人可读原因；
- 一条规范重试示例；
- 需要时附最新标签和最小新上下文。

## 8. 语言适用性

核心协议对语言无感：

- **Python**：逐字保留缩进；不做忽略空白的自动匹配；可选用 Python 解析器做提交后语法检查。
- **C/C++**：逐字保留预处理器和宏；格式化不是 Edit 的隐式副作用；可选 tree-sitter/LSP 验证块边界。
- **Elixir**：局部文本轨保持通用；已有 `Newbee.Tools.Structural` 可作为语法树轨，最终仍应提交到同一事务层。
- **CSS/HTML/Markdown/配置文件**：直接使用行范围协议，无须语言解析器。

后续的 `PUT N*` 语法块操作，只是由语言适配器把节点解析为 `N..M`，然后走同一套快照、冲突和提交逻辑。

## 9. 实现结构

建议把当前单文件实现拆成以下职责：

```text
Newbee.Tools.Edit                 对外门面与兼容层
Newbee.Tools.Edit.SnapshotStore   快照、标签、已读范围、LRU
Newbee.Tools.Edit.Parser          最小补丁语法
Newbee.Tools.Edit.Planner         坐标检查、重叠检查、候选生成
Newbee.Tools.Edit.Recovery        旧快照到当前文件的安全映射证明
Newbee.Tools.Edit.Transaction     锁、临时文件、回滚、journal
Newbee.Tools.Edit.Result          稳定结果和错误结构
```

兼容迁移：

1. 保留现有 `show/2`、`patch/1` 为 v1；
2. 新增 `show_v2/2`、`apply_v2/1`，先不改现有调用；
3. 建立基准后，把模型提示切到 v2；
4. 一段观察期后再决定是否删除逐行哈希协议。

## 10. 验证方法

不能只凭单次主观体验决定默认格式。需要做同模型、同任务、同工具集的对照实验：

- v1：逐行哈希锚点对；
- v2：文件快照 + 原始行范围；
- replace：快照 + 精确旧内容替换。

任务至少覆盖 Elixir、Python、C、JavaScript、HTML/CSS 和 Markdown，并包含：

- 单行替换；
- 多行替换、删除和插入；
- 同文件多个不相邻修改；
- 重复行和连续空行；
- Python 缩进；
- C 宏和续行；
- CRLF、BOM、无尾换行；
- 读取后在文件其他位置插入或删除；
- 目标范围内部发生并发修改；
- 多文件事务和写入失败。

核心指标：

1. 最终任务通过率；
2. 首次编辑调用成功率；
3. **静默错改数，目标必须为零**；
4. 工具参数输出 token；
5. 含重试在内的总 token；
6. 工具调用轮数和完成延迟；
7. stale 情况的安全恢复率与正确拒绝率；
8. 按模型、语言和编辑形状分组的结果。

只有在同一模型的对照结果表明 v2 更可靠或总成本更低，才把该模型路由到 v2。模型路由是基准结论，不是按品牌猜测。

## 11. 分阶段实施

### 阶段 A：修正文档和现有缺口

- 修正 v1 范围语法示例，使它与解析器真实要求一致；
- 为长范围中间被修改的情况增加回归测试；
- 给错误增加规范重试示例；
- 明确当前“原子”只指预检阶段。

### 阶段 B：最小 v2

- 快照存储和 12 位会话标签；
- 简单行号读取输出；
- `PUT N..M`、`PUT <N`、`PUT >N`、`CUT N..M`；
- 已读范围、重叠、no-op 和完整版本校验；
- 新标签、diff 和局部上下文返回。

### 阶段 C：安全漂移恢复

- 旧快照到当前文本的行映射；
- 整个目标范围不变证明；
- 插入点边界证明；
- 歧义和冲突的最新上下文反馈。

### 阶段 D：事务与基准

- 路径锁、临时文件、进程内回滚；
- 多语言编辑基准；
- 按模型固定协议路由；
- 记录实际失败类别，驱动后续优化。

### 阶段 E：可选能力

在数据证明有收益后再加：

- tree-sitter 块选择；
- 跨文件 cut/paste 寄存器；
- journal 崩溃恢复；
- 受约束解码语法；
- 格式化、解析、LSP 和测试后置条件。

## 12. 决策摘要

推荐的默认方向是：

> **模型只表达“基于哪个完整文件快照，把原始哪些行变成什么最终内容”；工具负责快照、消歧、漂移证明、事务和反馈。**

具体决策：

- 保留 hash 的价值，但把它从“每行都让模型抄”提升为“文件快照和内部验证机制”；
- 默认使用快照范围协议，不默认使用内容重抄；
- 精确内容替换保留为按模型实测选择的备用接口；
- 模糊匹配只提供建议，绝不自动提交；
- 不按编辑行数动态切换语法；
- 先保证零静默错改，再优化首次成功率、token 和延迟；
- 用可复现的同模型 A/B 基准决定最终默认值。
