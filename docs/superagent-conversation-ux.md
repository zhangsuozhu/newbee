# newbee 对话中的协作：使用方式与操作设计

> 当前使用方向已修订为**直接任务与自动分工**：在原项目对话输入目标，点击「分工执行」，系统安排分工、分别执行并统一集成。无需 GitHub、评论或来源配置；详见[直接任务操作](conversation-task-execution.md)。下文保留 v0.4 历史设计，外部来源不再是主产品路径。
>
> 状态：v0.4 使用设计已落地至原会话协作与受控来源接入。实际操作、验收证据和支持边界见[运行与验收](conversation-work-operations.md)；离线原型仍只演示交互，不连接真实执行。
>
> 配套：[可点击原型](superagent-conversation-prototype.html)、[后台融合设计](superagent-colony-integration-design.md)。原型只演示交互，不调用模型、不写代码、不连接真实项目。本文规定日常操作，后台设计必须服从这些行为约定。

## 1. 产品决定：用户继续用原会话

用户的日常入口是已经在用的 newbee 对话。输入需求、补充要求、查看结果、回答问题都在原会话完成。没有“先进入蜂群”的必经步骤，不要求建群、创建 Bee、给 AI 分角色、勾选成员或填写子任务表。

前台只让用户掌握三个概念：**当前项目、当前对话、正在做的工作**。Bee、Colony、Task、Honey、Workflow、执行代次是后台实现和诊断信息，默认不出现在主操作里。“蜂群”可保留在高级管理入口，不再成为另一套主产品。

保留普通对话习惯：问一个问题就回答，贴代码就分析；讨论方案不自动写文件；明确要求实现则按已有权限推进。不能把每条消息变成工作卡、要求验收的工单或模式选择。

首次使用只补当前操作缺少的必要条件：没选目录而用户要求修改文件时，就地选择一次项目根；模型凭据缺失时，在现有设置页提供明确修复入口。能正常对话的用户不重复配置；不能把后台内部建 Colony、成员和邀请的流程推给用户，也不能为了省步骤猜一个目录或身份。


### 1.1 已核对的事实与待验证判断

| 现有代码事实 | 可能带来的使用成本；需要操作验证 |
| --- | --- |
| `priv/web/colony.html` 是独立入口，可返回会话；主会话也已有待处理栏 | 用户可能要在会话/群/工作之间找入口，已有待处理栏未必解决上下文割裂 |
| `colony/composer.js:target()` 随 task/member/conversation 改变收件对象 | 输入框外观相近，但“这句会发给谁、算补充还是新工作”可能难判断 |
| `colony/workflow.js` 的 choosing 可要求勾选 Bee、填写交付目标及边界 | 用户承担了组织 AI 的工作；功能齐全不等于操作省事 |
| `colony/workbench.js` 有执行会话检查、引用与另开会话 | 查看细节的能力存在，但用户可能需要在多个上下文补话 |
| 主会话 `openWorkItem` 当前主要切到 task.session_id | 原请求对话、执行会话与工作记录不总是同一个面，用户可能失去原话位置 |
| `colony/workflow.js` 的集成说明要求独立目录、不自动写回源项目 | 看到成果不代表当前项目已发生修改；“怎么用”必须设计成闭环 |

这些是本轮取证支持的设计风险，不是对用户弃用原因逐项证实。不能用“加了按钮”替代对真实操作的验证。

## 2. 默认操作路径

| 用户要做什么 | 用户实际操作 | 系统必须完成的事 |
| --- | --- | --- |
| 普通问答、分析设计 | 直接输入，回车发送 | 保持原来的对话；不强制创建后台工作 |
| 当前项目做一个修改 | 在原对话说“帮我修复……” | 显示工作目录，在既有授权内实施、验证并报告结果；协作者由系统选择 |
| 做着其他事，让当前工作继续 | 点击当前工作上的“后台继续”，或说“这件事在后台做” | 保存目标/输入/位置与稳定 work ID；安全交接后原对话仍收到问题和结果 |
| 改变正在进行的要求 | 在原对话直接补一句 | 同一工作收到版本化补充；显示“已收到/已采用”；不新开重复工作 |
| 开一件独立工作 | 现有“新对话”，或明确说“另开一项……” | 给独立工作清楚的对话归属；旧工作继续，不把两份修改混在同一个写目录 |
| 看后台进展 | 看原会话的一行状态；需要细节时展开“查看过程” | 展示实际活动/更新时间，不伪造百分比，不强制跳执行会话 |
| 回答 AI 的问题 | 在原对话的问题卡上点选，或就地输入答案 | 关联正确问题 ID，记回执并继续；不要求再找“继续任务”按钮 |
| 结果不满意 | 在结果下继续说“这里还要……” | 验收前继续原工作；已完成后形成关联后续工作，前台保持同一脉络 |
| 成果在独立目录 | 看改动后点击“应用并完成” | 核对目标和版本，应用并验证；成功后记采用/完成；失败不误报成功 |
| 暂时不做/彻底不要 | 当前工作“暂停”/更多里的“结束工作” | 暂停与终止分开；实际停止前展示正在停止；保留已有修改和历史 |

日常不增加必须记住的斜杠命令。按钮提供明确入口，自然语言提供等价能力；不能仅靠关键词“方案”“继续”把用户送入一个无法退出的工作阶段。

## 3. 页面与导航

### 3.1 主界面沿用原布局

- 左侧继续是原会话列表与“新对话”。会话有后台工作时增加一个状态标记；“需要你处理”只是有真实待办时出现的小入口。
- 顶栏保留对话标题、项目/工作根和现有模型入口。切换项目是明确动作；正在运行的工作不会随全局选择静默迁移。
- 中间是同一条用户/助手对话。需要长期跟踪的工作以一个会更新的紧凑卡片挂在相关请求下面；不为每个工具事件追加一张卡。
- 底部继续使用同一个输入框、附件、发送、停止、原有快捷键。任何附加目标都在输入框附近显示，例如“补充：修复导出”；页面滚动、展开日志或切换查看项不改变收件对象。
- 过程、分工、执行目录、费用、验证日志放在当前会话的抽屉/折叠区；关闭后仍在原处，保留草稿、滚动和选区。
- 手机沿用同一主流程。详情全屏打开可返回，主输入框和当前工作不被固定侧栏遮挡。

一个问题/成果在工作卡、待处理列表和原会话出现时，都是同一对象的入口。点任一入口都定位到原会话的同一个决定，不能产生三组互相不同的状态与按钮。

### 3.2 工作绑定不能靠猜

对话里明确一个当前工作。新目标出现前，后续要求默认补到当前工作；纯状态问答可以直接回答，不启动第二个执行任务。

其他后台工作仍可继续；点开其过程只是查看，不能暗中把输入框切给它。若主动选择给另一个工作补话，必须显式点“回复此工作”，显示可取消的目标标签。

多个工作都可能匹配“继续这个”时，只问一个简短问题，给两三项可辨认的工作标题；不要求用户去工作台找 ID。新对话是最清楚的独立任务边界，现有用户无需学习新的组织方式。

## 4. 前台、后台与目录规则

### 4.1 当前会话直接执行：保持已有习惯

正常对话执行使用该 Session 已绑定的目录和权限，仍可能修改当前目录；必须在原有位置清楚显示目录。后台协作能力不能改变这一既有语义，也不能把已经产生的修改隐瞒成“等待应用”。

助手招募其他 Bee 时，其写入必须隔离。负责人在原执行边界内集成，继续遵守权限和版本检查。用户只看一个总结，不管理协作者的 Session、worktree 或子任务验收。

### 4.2 后台继续：一次交接，身份不变

“后台继续”是运行方式，不是新目标或重复建单。目标、Task/输入、问题、原对话、实际工作目录保持关联；关闭浏览器不表示取消工作。必须实际持久化并完成安全交接后，才显示“已在后台继续”。

后台不能同时写一个仍由前台/用户编辑的目录：

1. 没有写入且能安全开始隔离时，在独立目录启动；原卡显示“独立工作区，结果需应用到项目”。
2. 前台已经修改了文件时，默认保留现有 Session/Workspace，只把显示/调度转为后台；明确提示本工作仍使用哪个目录。不能无提示换目录、复制用户脏改或重复执行上轮命令。
3. 如果该目录需要立即让给另一个写工作，先到安全点暂停当前写入，再基于已确认的快照隔离；无法可靠隔离则清楚说明限制并给“保持当前执行/暂停后另开”。
4. 新独立写工作默认使用独立 Workspace。两个来源相同的目录也不等于可以同时写。

首版可以只支持“从一个明确请求开始隔离后台工作”，暂不支持运行中迁移。按钮必须反映实际支持，不能先设计一个无条件“一键后台”却让后台复制上下文丢工作。

## 5. 六条必须走通的使用故事

### A. 一句话开始，小改动直接完成

用户在已选项目会话里输入“修复导出 CSV 时日期为空的问题，加上相关测试”。系统接住目标，按权限执行；内部判断是否协作。用户无须选成员、填表、逐阶段说继续。结果说明改了什么、验证如何、文件在哪里。

如果当前目录已改，结果标“已修改当前项目”，只有“查看改动/继续修改”这类必要动作。不能再给“应用到项目”按钮让用户重复应用。普通问答完成也不弹验收表。

### B. 后台工作，用户离开再回来

用户明确“在后台做，完成告诉我”。若可隔离，则请求下显示一张卡：“修复 CSV 导出 · 进行中 · 独立工作区”，可暂停/查看过程。用户打开新对话处理别的事；原会话完成后显示一个需查看标记。

刷新或重启恢复时，对话、草稿和工作由服务端持久事实恢复，不能因前端 localStorage 有卡就声称进程还在跑。确实不能确认执行状态时直接进入恢复检查。

### C. 中途改需求

用户补充“别改现有日期格式，只补空值”。消息先显示“已收到，等待在下一安全步骤采用”；模型请求确实包含该补充后再改成“已采用”。如果已经写过相关代码，负责人重新核对并修正；不把用户补充当新任务排在旧任务完成后。

急迫“停一下”优先控制，不作为普通聊天排队。用户误发/重复点发送都使用稳定 message/request ID；发送结果不明可以查回执，草稿不会凭一个网络错误消失。

### D. 真正需要业务决定

系统遇到两种会影响使用者的行为，例如“空日期保留空白还是显示未提供”。原对话给一个问题，说明差异和推荐；按钮写行为含义，不写 Bee 名字。

选择即记录答案并继续；自由文本也可在同一卡片就地回答。没有变化的授权不重新问；“这段由谁实现、几只 Bee、下一步调用哪个工具”不是让用户决定的业务问题。

### E. 结果可检查、可采用、可继续修改

独立 Workspace 的结果卡展示：目标与结果摘要、变更文件和差异、验证结果/未验证、目标目录、准备应用的版本。用户可“继续修改”，或查看后“应用并完成”。这一个动作明确表达采用当前版本并写入指定项目；系统把 review/apply/check/finalize 作为可恢复步骤。

有用户新改动、基线变化或冲突时保留原文件，显示“目标已变化，需要重新核对”，提供“重新比较”而不是让人复制 patch 或重做任务。不能在失败后先把 Honey 标为已完成。应用成功但最终回执/验证未完成时，显示“已应用，检查待完成”，重试只做剩余步骤。

非代码成果（分析、文档草稿）直接在原对话可阅读/复制/下载，不要求应用文件或打开一个“成果中心”。后台工作如需关闭记录，可在同一处“确认完成”；不逼每条助手回复走验收。

### F. 失败恢复与放弃

短暂 provider 错误由系统自动退避，卡显示原因与下一次处理，不连续通知。确实需要人时说清楚卡在哪里、已有改动如何保留、建议的下一动作。

用户点“继续处理”复用同一工作、同一明确输入和检查点；不新建重复工单，不重放已发生的外部操作。“结束工作”停止推进，保留已有修改；它不等于回滚。回滚是另一个以真实差异为依据、需确认影响的动作。

## 6. 主动作与文案规则

| 用户可见状态 | 默认主动作 | 辅助动作/约束 |
| --- | --- | --- |
| 正在处理 | 不催促操作，保留输入可补充 | 暂停、查看过程；停止入口可达 |
| 已收到补充 | 无需用户再次点继续 | 未实际采用前不能标已采用 |
| 需要你决定 | 具体选项/就地回答 | 可稍后；没有回答不默认批准 |
| 暂停中 | 等实际确认 | 不能先显示已暂停；超时展示无法确认 |
| 已暂停 | 继续 | 结束工作；其他输入不解除暂停 |
| 自动重试 | 无需人操作 | 显示下一次处理；手动重试不并发启动第二执行者 |
| 执行状态无法确认 | 检查并恢复 | 不写“继续”并盲目双开；查看已有改动/结束 |
| 可采用的独立结果 | 应用并完成（有权限且版本有效） | 查看改动、继续修改、稍后 |
| 已改当前项目 | 查看改动 | 继续修改；不重复显示应用 |
| 结果基线过期 | 重新比较 | 保留现有文件；冲突说明到文件级 |
| 已完成 | 结果可直接使用 | “继续修改”创建关联后续工作，复用背景；不让用户先填新表 |
| 已结束 | 历史和现存改动可查看 | 明确新请求才能再工作，机器事件不能复活 |

正常工作卡最多一个强调的主动作。停用按钮有原因，不靠灰色猜。菜单中的“隐藏提醒”“暂停”“结束工作”“撤回文件修改”必须区分，避免用户为清理待办误取消任务。

## 7. 输入、控制与可访问性

- Enter 发送、Shift+Enter 换行沿用用户现有偏好；中文输入法 composing 时 Enter 不发送。切换工作、开关抽屉不能吞草稿。
- busy 时输入框能补充；发送时显示其目标和处理状态。等待停止确认期间控制按钮可见，重复点击幂等。
- 粘贴、拖拽和附件使用原入口；上传失败保留文字和文件选择。无可用执行会话时先建立正确的资源归属，不要求用户为了上传先选 Bee。
- Esc 保留现有停止行为，但不会关闭对话/取消工作记录；“暂停/停止/结束”通过一致文案和回执区分。危险撤回和外部发布仍遵守实际授权。
- 所有关键动作有键盘焦点、明确名称与状态反馈；弹窗/抽屉关闭后焦点回到触发按钮。手机主动作触控目标至少 44px；状态不只用颜色表达。
- 不自动抢滚动到最新一行，不清空用户正在写的答案；新问题/结果以定位入口提示。屏幕阅读器只读必要状态变更，不播每个 token。

## 8. 用户习惯与发布迁移

现有主会话是默认，不把旧用户重定向到 colony.html。已有模型选择、目录、快捷键、会话标题与搜索保留。协作行为加入同一会话背后，不改用户的第一步。

旧群、成员、历史 Task/Honey 不删除，也不批量启动；放在“历史协作/高级管理”可检索。用户点旧工作能看到状态和结果，选择“在当前对话继续”时建立显式关联和权限检查，不复制整个任务再执行一遍。

没有必要让每个普通 Session 都注册成一只 Bee。仅在需要持久后台工作/协作时按明确项目范围懒初始化内部能力。任何自动绑定的可见性都不能跨项目或跨认证域泄漏。

第一阶段 opt-in，只对试点项目启用新工作卡/后台入口；退出试点后原普通会话仍能用，受理过的工作保留查询、停止、结果领取和人工接续通道。

## 9. 为这个用法必须改的后台边界

| 用户承诺 | 后台必须补齐；不能由前端演出来 |
| --- | --- |
| 原会话接着说 | origin_session_id、current_work_ref、输入/问题/成果引用；查看 Session 与发送目标分离 |
| 已收到/已采用可信 | message receipt、队列接收与模型真正消费分别记录；可恢复的 request id |
| 自动安排协作 | 现有 Workflow choosing 不能把人员勾选和子任务表当必经门；负责人给推荐并在授权内自行分工 |
| 只有业务决定问人 | 当前 proposal/choosing 等待要区分用户明确“先出方案”与系统内部协作；不能统一要求手动批准下一阶段 |
| 后台不会双写 | 单一有效 execution_generation、Control 停止回执、隔离 Workspace；原 Session 绑定的明确迁移协议 |
| 原对话收到结果 | Runtime → 原会话的持久通知/投影；不能只发到工作 Bee 的执行会话 |
| 应用并完成不会毁现有改动 | Colony 专属的差异审阅、目标/基线/hash 校验、幂等应用回执和 finalize；不能拿 CrossHost group.workspace.apply 冒充 Colony 已支持 |
| 刷新不丢工作和问题 | 同一存储提交 Task/Input/Question/Delivery/receipt，真实恢复流程；WebSocket 只传视图更新 |
| 用户不用管理内部对象 | 默认不展示建群/配 Bee；成员和调度管理保留在高级面；只迁移必要写路径 |

v0.3 中“P0 不改变现有 Workflow 默认”与本设计冲突：如保留强制 choosing/分工表，用户体验仍无法成立。修订为：先验证交互，再只为明确授权的执行工作增加由负责人自主推进的路径；用户说“先讨论/先出方案”仍停在方案结果，不擅自实施。

## 10. 先验证能用，再实现

### 10.1 原型评审

打开配套 HTML，不需要启动模型/服务，演示“后台请求 → 补充 → 问题 → 结果 → 应用/冲突 → 恢复”。演示输入和结果都有标记，不证明真实系统已经支持。

请真实用户按自己的话完成以下任务，不事先讲 Bee/Task 概念；观察停顿、误点与理解，不能把设计者自己走通算成用户验证：

1. 发起一个项目修改，不建群、不选人；
2. 把工作留在后台，并在另一个对话做事；
3. 回来补充要求，判断是已发送还是已经被采用；
4. 找到并回答问题，不误发到其他工作；
5. 判断当前项目是否已经修改，使用后台成果；
6. 遇到连接中断、目标冲突或未知执行状态，保留现存工作并正确恢复；
7. 暂停后明确继续；终止后找到已有改动；
8. 已完成后返修，不重新复制背景或填写任务表。

### 10.2 目标与门槛（尚未测量）

- 在已打开项目会话前提下，普通请求是“输入 + 发送”；新增必填组织配置、必选 Agent、必填分工表均为 0。
- 从原对话收到问题到答复，不跨页面；答案点击/发送一次即可，不需再点继续。
- 单个工作结果的查阅、返修和正常采用都在原对话；执行会话不是必经操作。
- “这句发给谁、是否采用、文件在哪里、现在该做什么”应由界面直接回答；用户无需猜。
- 所有恢复场景不得丢草稿、隐匿已有改动、重复建单或启动第二写执行者。
- 与旧版和现有普通会话比较完成率、误路由、人工操作数、任务用时、返工及用户愿不愿继续使用；首次试用发现的概念障碍优先改设计，不先加更多说明书。

当前待验证的偏好包括后台入口的频率、直接执行/后台隔离的预期、完成结果怎样才算省事。它们不阻止出原型，但未经用户试用不能定为最终默认。

## 11. 交付顺序

1. **交互验证**：先评审这份操作规范和原型，删掉用户走不通的步骤；不能先把整套协议做完再包装 UI。
2. **主会话最小可用版**：现有会话内跑通一个明确工作，补充/问答/状态/结果原地完成，去掉内部人员选择；暂不接外部 Source。
3. **可靠后台与采用**：隔离启动、单执行者、断线/重启恢复、版本校验应用与结果回原会话。功能未通过前不对所有工作显示后台/应用按钮。
4. **迁移与真实使用**：一个试点项目日常用，记录失败和弃用信号；旧版仅保留历史与高级能力，不增加迁移负担。
5. **外部接入**：同一交互/责任语义稳定后再接 GitHub/飞书。外部原线程就是用户的原对话，不要求切到 newbee 工作台才能处理。
