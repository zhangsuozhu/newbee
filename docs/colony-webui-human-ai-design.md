# Colony Web UI：有取舍的人机协作方案

状态：方案第一批 A 已实施；历史游标分页已实施；相同验收决定已实现状态幂等；通用持久操作回执尚未实施。评审基线：`feat/colony-suite@1de767ad01d33f0573c9e422b9a0c8010fb82278`。

## 1. 核心决策

保留 Task / Workflow / Honey / Trace 为核心的工作中心。借鉴 agent-git 对会话阅读、数据来源、只读观察、连接状态和分享范围的清晰表达；不把 Colony 改造成会话 Git 平台。

首批只解决：人能知道下一步；人能有依据地验收；人能明确、可靠地干预。更多 Agent、讨论轮数、日志数量不等于协作价值。

本方案补充 [Aily 改进计划](webui-aily-improvement-plan.md)，复用其分栏、导航、关闭、焦点及草稿规则。旧计划的问题列表是历史观察，不全部视为当前缺陷。

## 2. 证据范围与当前实现

本轮已 fetch `origin/feat/colony-suite`；本地/上游差异 `0 / 0`，研究前工作区干净，无须 merge/rebase。

newbee 当前已有：

- `store.js`：URL 恢复、请求序列防串页、attentionTasks、3 秒可见页面轮询。
- `composer.js / workbench.js`：按工作保存草稿、执行检查面板、显式指导、关闭恢复上下文。
- `drill.js`：概览、协作记录、执行观察、成果验收、历史。历史明确没有不可变快照，不提供恢复按钮。
- `Honey`：pending_review / auto_verified / accepted / rejected；`Work`：成果与 context_revision 对应检查。应复用而非另造验收系统。
- `Trace / Store`：稳定记录 ID/seq。概览取最近 200 条公开记录；任务详情取本任务 100 条、每个子任务最多 40 条。底层有 since_seq，但当前 colony.trace.list 没有完整的向前分页/覆盖范围契约。

上一轮只读浏览器测量：1440×900 下侧栏 264px；390×844 下主区宽 390px、侧栏移出屏幕、输入区高 132px。这只证明基础响应式存在，不证明所有弹层、软键盘、键盘导航通过。

agent-git 克隆版本：`134fec0400d98addca6fee23b7212c4a87b78707`。完整 Web 源码所在服务端仓库需认证。上一轮实际读取了公开部署的 SessionView、SessionChrome、Events、WorkspaceLive、Search 及 CSS 构建产物；它们证明发布代码中存在相关机制，不能代表登录态全路径实测成功，也不能保证与克隆提交相同。匿名浏览器当时取得壳层/Loading。web-controller-migration 文档标为进行中，设计要求不能冒充已交付行为。

可核查的 Web 长处：按 turn 的会话目录和定位；工具折叠/展开/隐藏；独立文件变化视图；只读历史与实时跟随区分；显示历史保存时间和近期窗口；分享前预览独立副本；搜索区分原始发言与压缩摘要，不完整搜索不冒充无结果。

## 4. 明确的取舍

| 候选 | 决定 | 原因 |
| --- | --- | --- |
| 注意力队列 | 保留精修 | 已有基础；按当前用户责任与权限统一原因、计数、动作 |
| 证据优先验收 | 首批重点 | 利用 Honey/acceptance/checks，直接改善人的判断任务 |
| 执行目录、引用定位 | 选择性吸收 | 工作层用里程碑，执行层用 turn，不把所有事件灌进首页 |
| 只读观察/显式指导 | 补强已有实现 | 查看不能改变主输入目标；引用保留来源 |
| 回执/结果待确认 | 第二批重点 | 先做发送、继续、暂停/中止、验收，不重写全部 RPC |
| 历史分页和覆盖说明 | 第二批基础能力 | 最近 N 条不是完整历史，与是否使用 WebSocket 无关 |
| 固定三栏、全量 ID/cwd/seq 常显 | 不采用 | 分散注意力；按需辅助面板，元数据进入详情 |
| 全程推理展示、Agent 同意率、置信度百分比 | 不采用 | 解释不是证据，多 Agent 不等于独立验证；不展示未校准概率 |
| 会话 Git fork/merge/完整恢复 | 暂缓 | 与代码工作区、远程执行、外部副作用语义不同 |
| 公共广场/排行/星标/社交资料 | 不采用 | 资产传播不是当前协作执行目标 |
| 加密外链分享/复杂组织体系 | 暂缓 | 先打通权限内任务/成果深链接 |
| 全局单人驱动锁 | 不照搬 | 会阻碍 Bee 并行；若出现同会话冲突指导，再考虑局部租约 |
| 立即替换轮询为 WebSocket | 暂缓 | 先测详情请求与渲染成本，修状态与分页再选传输 |
| React 全量重写 | 不采用 | 现有模块可增量演进，框架不是主要矛盾 |

修正上一轮过宽的 P0：不先造完整事件 DTO、所有写操作回执和不可变版本平台。先选用户路径，补它需要的最小契约。

## 5. 推荐体验：工作 → 证据 → 干预

### 5.1 工作列表：下一步明确

卡片默认只留标题、负责人、需要处理的原因、更新时间和一个主操作。完整路径、内部阶段、上下文修订号放详情；目录异常时例外显示有用路径提示。

“待我处理”按当前操作者计算，区分等我答复、等他人、执行失联、等我验收。内部子成果由协调者整合，不重复索取人工验收。列表、计数、主动作共用投影。

当前 `chat.js` 在待处理为空时会自动选进行中。建议默认选择只用于首次进入；用户主动选择的筛选保持不变，不在 render 中跳页。

### 5.2 详情：保留已有五分区

- 概览：目标、验收条件、负责人、障碍、下一步。
- 协作记录：责任、依赖、交接、未解决分歧、改变计划的决定。
- 执行观察：阶段摘要与关键事件；详细工具记录按需展开。
- 成果验收：本次交付的证据包，待验收主按钮直接进入这里。
- 历史：按决定/执行/提交/验收定位，显示覆盖范围，不制造恢复按钮。

宽屏按需打开辅助面板；不开时主内容独占可用区域。手机单面板全宽，返回保留工作和阅读位置。首批保留路由和标签，不另外增加同义导航。

### 5.3 验收页：建议、证据、局限相邻

以下是设计示意，非实际测试结果：

```text
工作：登录刷新修复    负责人：auth-bot    待你验收
本次交付                     [查看修改] [打开成果]
验收条件                 证据                   状态
并发刷新不重复请求         定向测试执行记录        已验证
旧会话可以继续             暂无记录               未验证

未验证项/限制：……      代码基线：匹配 / 已变化 / 未知
[接受这次交付] [提出修改]   更多：执行记录
```

工程任务展示 diff、测试结果及基线；研究任务展示来源/引文/未知项；文档任务展示内容与要求对照。共用 Honey 外壳而非统一成代码审查。

自动预检通过不显示为人已验收。AI 自报“测试通过”仅算报告，只有可定位执行记录支持时才算验证。多个 Bee 引用同一日志仍是一份证据。基线变化保留旧证据并标记适用范围，不擅自重跑。

证据充分的普通验收保持直接操作；缺证据时允许人在授权范围内明确接受局限并记录判断。硬性权限/基线门禁不能由前端确认绕过。不增加逐条“我已阅读”仪式。

### 5.4 干预：范围明确且可纠正

打开 inspector 默认只读；点击“指导这次执行”后显示负责人、关联工作和接收对象。关闭只收起观察，不暂停运行。主输入仍属于当前工作。

引用是可移除来源块，带工作/会话/事件/成果身份，能打开原记录。摘要标记为摘要，不冒充原话；文本引用作为兼容表示而非唯一关联。

补充要求沿用工作；修改目标使用 Work.revise/context_revision；暂停、中止为独立明确动作。已完成工作通过显式后续任务继续，不悄悄复活旧执行。

### 5.5 三类状态不能混成一个绿点

| 对象 | 用户问题 | 展示 |
| --- | --- | --- |
| 页面同步 | 数据新吗 | 最后成功时间；失败保留旧数据，提示暂不能更新 |
| 执行实例 | Bee 还在工作吗 | 执行中、等答复、暂停中、已暂停、无法确认 |
| 某次操作 | 指令生效了吗 | 提交中、接收、排队、生效、拒绝、结果待确认 |

只按事实展示。排到工具边界不等于模型已读；页面断网不等于任务停止，也不能只凭旧心跳保证执行正常。

未知结果先按稳定 operation_id 查回执。重试同一意图复用 ID，新意图用新 ID。等待确认期间仍可编辑下一条草稿。收到暂停请求与执行器确认暂停是两种状态。

## 6. 工程落点与不变量

| 模块 | 最小增量 |
| --- | --- |
| Task / Work / Workflow | 复用状态机与修订校验，输出动作原因，不在浏览器重新编排 |
| Honey / 提交验收路径 | 补证据引用及交付基线，复用预检/人工验收分离 |
| Trace / Store | 复用 ID/seq，补 before_seq、范围和分页 |
| ColonyApi | 逐对象 allowed_actions + reason；写时重新授权；首批关键操作回执 |
| store.js | 保留防串页；资源级 loading/error/lastSuccessAt 与范围 |
| chat/taskcard/workflow | 共用用户状态与主动作映射，避免重复计数和跳页 |
| drill/workbench | 成果证据、里程碑、历史覆盖、来源引用 |
| composer/api | 草稿与待确认操作按范围隔离；错误留在发生处 |

历史建议接口：请求 scope、before_seq、limit、upper_seq；响应 items、next_before、has_more、upper_seq、coverage。首次固定上界，向前分页保持该上界，新事件单独合并。scope 和权限始终校验。按 ID 去重，不按相同文本去重。全局 seq 被不同记录共用，间隔不等于丢事件。错误保留已读内容。

这利用 newbee 追加 Trace 的特点，不复制 agent-git 原生文件/SQLite 快照系统。若未来允许改写历史再升级一致性契约。

回执先检查现有 deliveries/command_id/CAS，扩展已有路径，不造第二个队列。稳定键绑定操作者、目标、操作类型、意图 ID；去重与权威变更必须事务一致或可恢复。rpcId 仅是请求关联，不自动等于业务幂等键。

权限区分观察、指导、控制、验收、管理，前端显示原因，后端执行时重查。无需一次引入完整组织权限模型。

现有 sinceRevision 在 Engine 构造视图后比较指纹，主要节约传输和重渲染，不应声称已消除后端全量计算。先量 overview/drill，再决定缓存、详情 revision 或推送。

保留主题系统，用层级、间距、语义色降低噪声；状态必须有文字。窄屏正文优先、目录折叠、隐藏导航隔离焦点。含内嵌操作的交互行不能简单换成嵌套 button，需拆主导航与行内操作。

## 7. 实施顺序

### A：可判断、可验收

状态/主动作投影、保持筛选、证据矩阵、未验证/基线提示、复用 inspector。无需新 Agent 编排或版本库。

退出条件：待处理直接到对应问题/成果；用户能定位修改、证据和限制；关闭检查后工作/草稿/位置不变；普通成员不会获得管理专属主动作。

### B：不丢历史、不重复干预

Trace 向前分页与范围说明；关键操作稳定回执；连接、执行和操作状态分离。

退出条件：超过 200 条可回读；追加中翻页不重不漏；响应丢失后重试不重复效果；旧响应不写入新工作；未知状态不伪造成功且草稿可编辑。

### C：有需求证据才扩展

先做权限内任务/事件/成果深链接。实际需要跨项目交接时再做审阅导出；明确代码快照与外部副作用边界后再讨论 fork/恢复。首版不承诺 C。

## 8. 验证方法

尚未建立人机协作绩效基线，不承诺提效百分比。建议先用 6–8 位熟悉度不同的开发者做形成性走查，固定数据、交替界面顺序；用于发现问题，不宣称统计显著。

场景：接手离开 30 分钟的工作；三项工作同时待处理；正确成果有未验证项；看似合理但基线过期的成果；发送成功响应丢失；阅读 300 条以前历史；只读成员观察；手机查看成果再回草稿。

测量：找到下一步耗时、辨认责任/输入对象准确率、证据定位耗时、误验收数、重复操作数、丢草稿/位置数、主观工作负担与阻碍感。误验收与重复执行优先于少点一次；不以消息数量、停留时长或 Agent 同意率衡量成功。

工程门禁：深链接/返回/焦点/草稿；过期响应；断网回执；历史追加与分页；权限拒绝；中文长标题、窄屏、软键盘、键盘操作。用隔离 fixture，不自动唤醒真实 Bee 或付费模型。源码字符串测试不能代替真实浏览器验证。

性能以同一 fixture 记录 overview/drill 请求数、字节、延迟、渲染次数，再选择优化。不能靠显著增加等待换取表面信息更全。

## 10. 第一批实施记录

- 新增 workview.js：共同的责任/动作投影与成果审阅模型；计数复用于顶栏、侧栏、工作列表和待处理面板。其他真人负责的阻塞工作不伪装成自己的待答复；人工验收只面向管理角色。
- 保留用户选择的筛选，不再因待处理为空自动切页。任务/流程卡增加直接处理入口。
- 成果详情从 drill.honey 与完整传入成果读取，修复只有最近成果能显示完整内容的问题；预检读取 review.auto_checks。
- 展示验收条件矩阵、检查报告、未验证项/限制和按记录 ID 去重的执行引用。执行摘要不被解释成验收通过。

## 12. 第二批 B-2：验收重试边界

相同的 `accept` 或相同的 `reject` 验收请求会返回已持久化成果，不重复提升任务 revision，也不追加重复 trace；相反结论仍返回错误。`work.submit` 对已有待验收成果继续拒绝重复提交。网络超时仍按“结果可能已处理”提示用户刷新确认，未把客户端重试次数伪装成服务端幂等键。

因此当前交付的是状态机级的验收重试安全，不是所有 RPC 的操作回执协议。跨请求幂等键、调用者可查询的回执表、崩溃恢复后的提交关联和完整恢复仍留在后续阶段。
